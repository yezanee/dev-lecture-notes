# 섹션 1: 예제 만들기 - 로그 추적기

---

## 요구사항

- 모든 PUBLIC 메서드의 호출과 응답 정보를 로그로 출력
- 애플리케이션의 흐름을 변경하면 안됨
- 메서드 호출에 걸린 시간, 정상/예외 흐름 구분
- 메서드 호출의 깊이 표현, HTTP 요청 구분(트랜잭션 ID)

## 뭘 하고 싶은 건가?

웹 서비스에서 사용자 요청이 들어오면, 그 요청이 **어떤 경로를 거쳐서 처리되는지** 추적하고 싶음.

```
[abc123] Controller.request() 시작
[abc123] |-->Service.order() 시작
[abc123] | |-->Repository.save() 시작
[abc123] | |<--Repository.save() 끝 (1004ms)
[abc123] |<--Service.order() 끝 (1014ms)
[abc123] Controller.request() 끝 (1016ms)
```

이렇게 보면 한 요청이 어디서 시간을 많이 잡아먹는지, 어디서 에러가 나는지 한눈에 파악 가능.

## 핵심 클래스

- **TraceId**: 트랜잭션ID(UUID 앞 8자리) + level(깊이) 보관. `createNextId()`로 같은 ID에 level+1 생성.
  - "이 요청은 누구 것인가?"를 나타내는 ID + 깊이 정보
- **TraceStatus**: 로그 시작 상태 정보 (traceId, startTimeMs, message). 종료 시 소요시간 계산에 사용.
  - 끝날 때 "몇 ms 걸렸는지" 계산하려면 시작 시간을 기억해야 하니까.

## V2: 파라미터로 넘기는 방식

Controller → Service → Repository로 호출할 때, TraceId를 **메서드 파라미터로 계속 넘김**.

- `begin()`: 최초 호출(level 0)에서 사용
- `beginSync(TraceId beforeTraceId)`: 이후 호출에서 사용, level 증가

```java
// Controller
orderService.orderItem(itemId, traceId);  // traceId를 넘김

// Service  
orderRepository.save(itemId, traceId);    // 또 넘김
```

## 이 방식의 문제점

- **모든 메서드 시그니처를 바꿔야 함** — 로그 하나 찍겠다고 인터페이스까지 전부 수정
- 첫 호출은 `begin()`, 이후는 `beginSync()` — 호출 구분이 필요

> **비유**: 회사에서 문서에 결재 도장을 찍으려고, 모든 서류 양식에 "도장 칸"을 추가하는 꼴.
