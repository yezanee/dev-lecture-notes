# 섹션 2: 쓰레드 로컬 (ThreadLocal)

---

## 필드 동기화의 동시성 문제

"파라미터로 넘기기 귀찮으니, 그냥 빈의 필드에 저장하자!" → TraceId를 싱글톤 빈의 필드에 저장하면 여러 쓰레드가 동시 접근 시 데이터가 섞임. 여러 쓰레드가 동시에 같은 인스턴스의 필드 값을 변경하면서 발생하는 문제.

> **비유**: 화이트보드가 1개인 사무실에서 두 팀이 동시에 메모를 적는 것. 서로의 메모를 덮어씀.

> **참고**: 동시성 문제가 발생하지 않는 경우:
> - **지역 변수**: 쓰레드마다 별도 메모리 영역이 할당되므로 안전
> - **읽기만 하는 경우**: 값을 변경하지 않으면 여러 쓰레드가 동시에 읽어도 문제 없음

## ThreadLocal이란?

해당 쓰레드만 접근할 수 있는 특별한 저장소. 각 쓰레드마다 별도의 내부 저장소를 제공하여 동시성 문제를 해결.

> **비유**: 쓰레드마다 **전용 사물함**을 주는 것. 각 쓰레드가 자기 사물함에서만 꺼내 쓰니까 절대 섞이지 않음.

```java
// 사용법
ThreadLocal<String> nameStore = new ThreadLocal<>();
nameStore.set("value");    // 저장 (내 사물함에 넣기)
nameStore.get();           // 조회 (내 사물함에서 꺼내기)
nameStore.remove();        // 제거 (내 사물함 비우기)
```

## ThreadLocalLogTrace 구현

`TraceId traceIdHolder` 필드를 `ThreadLocal<TraceId>`로 변경하여 동시성 문제 해결.

```java
private ThreadLocal<TraceId> traceIdHolder = new ThreadLocal<>();

traceIdHolder.set(value);   // 내 사물함에 넣기
traceIdHolder.get();        // 내 사물함에서 꺼내기
traceIdHolder.remove();     // 내 사물함 비우기
```

## 주의사항 (매우 중요)

쓰레드 풀 환경에서 ThreadLocal 사용 후 `remove()`를 호출하지 않으면:

1. 사용자A 요청 → thread-A에 데이터 저장
2. 응답 완료 → thread-A를 쓰레드 풀에 반환 (데이터 남아있음)
3. 사용자B 요청 → thread-A 재할당 → **사용자A의 데이터가 반환됨** (보안 문제)

**반드시 `ThreadLocal.remove()`를 호출하여 값을 제거해야 한다.**

> **비유**: 사물함을 비우지 않고 퇴근 → 다음 날 다른 사람이 같은 사물함 배정받아서 내 물건을 봄.
