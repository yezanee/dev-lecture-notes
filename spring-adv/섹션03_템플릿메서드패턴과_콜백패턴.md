# 섹션 3: 템플릿 메서드 패턴과 콜백 패턴

---

## 문제 인식

로그 추적기 도입 후 부가 기능 코드(try-catch, 로그)가 핵심 기능보다 많아지고, 모든 클래스에 반복됨.

```java
TraceStatus status = null;
try {
    status = trace.begin("message");
    // === 핵심 로직 (이 부분만 다름) ===
    trace.end(status);
} catch (Exception e) {
    trace.exception(status, e);
    throw e;
}
```

100개 메서드면 이 틀이 100번 반복. **변하는 것(핵심 로직)과 변하지 않는 것(부가 로직)을 분리**해야 함.

## 템플릿 메서드 패턴

부모 클래스에 변하지 않는 템플릿(골격)을 두고, 변하는 부분은 자식 클래스에서 오버라이딩.

> **비유**: 붕어빵 틀(=템플릿)은 고정이고, 속 재료(=핵심 로직)만 바꾸는 것.

```java
public abstract class AbstractTemplate<T> {
    private final LogTrace trace;

    public T execute(String message) {
        TraceStatus status = null;
        try {
            status = trace.begin(message);
            T result = call();  // 변하는 부분 — 자식이 구현
            trace.end(status);
            return result;
        } catch (Exception e) {
            trace.exception(status, e);
            throw e;
        }
    }

    protected abstract T call();
}
```

**한계**: 상속을 사용하므로 자식이 부모에 강하게 결합됨.

## 전략 패턴

상속이 아닌 **위임(조합)** 으로 문제 해결. Context가 Strategy 인터페이스에만 의존.

> **비유**: 붕어빵 기계 사장님(Context)에게 "이 레시피(Strategy)대로 만들어주세요"라고 넘기는 것.

- **ContextV1 (선 조립 후 실행)**: 생성자로 전략을 주입받아 필드에 보관
- **ContextV2 (파라미터 전달)**: 실행 시점에 전략을 파라미터로 전달 — 더 유연

## 템플릿 콜백 패턴

ContextV2처럼 전략을 **파라미터로 전달**하는 방식. 스프링 내부에서 자주 사용됨.

**콜백이란?** 다른 코드의 인수로 넘겨주는 실행 가능한 코드. 내가 "이 코드 나중에 실행해줘"라고 넘기면, 받은 쪽이 적절한 시점에 **되돌려(call back) 실행**해주는 것.

- `JdbcTemplate` → SQL 실행 전후의 반복 로직 처리
- `RestTemplate` → HTTP 호출 전후 처리
- `TransactionTemplate` → 트랜잭션 시작/커밋/롤백 처리
