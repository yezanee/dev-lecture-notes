# 섹션 4: 프록시 패턴과 데코레이터 패턴

---

## 프록시란?

클라이언트와 서버 사이에 위치하여 대리자 역할을 하는 객체. 서버와 같은 인터페이스를 사용하므로 클라이언트는 프록시 사용 여부를 모름.

> **비유**: 연예인(실제 객체)의 매니저(프록시). 팬(클라이언트)이 연예인에게 요청하면 매니저가 먼저 받아서 처리함. 팬 입장에서는 매니저한테 얘기하든 연예인한테 직접 얘기하든 결과는 같음.

핵심 조건:
- 프록시와 실제 객체는 **같은 인터페이스** 사용
- 클라이언트는 프록시인지 실제인지 **모름**

## 프록시의 주요 기능

둘 다 프록시를 사용하지만 **목적이 다름**:

| 목적 | 패턴 | 비유 |
|------|------|------|
| 접근 제어 | 프록시 패턴 | 경비원 — 못 들어가게 막거나, 캐싱(한번 확인한 건 다시 안 물어봄) |
| 부가 기능 추가 | 데코레이터 패턴 | 선물 포장 — 내용물은 그대로인데 포장지(기능)를 덧붙임 |

## 프록시 패턴 — 캐싱 예제

```java
public class CacheProxy implements Subject {
    private Subject target;      // 진짜 객체
    private String cacheValue;   // 캐시

    @Override
    public String operation() {
        if (cacheValue == null) {
            cacheValue = target.operation(); // 첫 호출만 실제 실행
        }
        return cacheValue; // 이후는 캐시 반환
    }
}
```

> **비유**: 처음 물어볼 때만 창고(DB)에 가서 확인하고, 이후엔 메모해둔 거 바로 대답.

## 데코레이터 패턴 — 체이닝

여러 데코레이터를 체인으로 연결 가능:

```
클라이언트 → 시간측정 데코레이터(TimeDecorator) → 메시지꾸미기 데코레이터(MessageDecorator) → 진짜 객체(RealComponent)
```

> **비유**: 선물에 리본 달고 → 포장지 씌우고 → 쇼핑백에 넣기. 순서대로 기능을 덧씌움.

## 인터페이스 기반 vs 클래스 기반 프록시

| 구분 | 인터페이스 기반 | 클래스 기반 |
|------|----------------|-------------|
| 장점 | 상속 제약 없음, 역할과 구현 분리 | 인터페이스 불필요 |
| 단점 | 인터페이스 필요 | 부모 생성자 호출 필수, final 사용 불가 |

## 문제점

프록시 클래스를 대상 클래스마다 하나씩 만들어야 함. 100개 클래스면 100개 프록시 필요. 하는 일(로그 찍기)은 거의 같은데!

> **비유**: 아파트 100세대에 경비원을 한 명씩 배치하는 꼴. 하는 일은 다 같은데 100명 고용.

→ **동적 프록시로 해결**
