# 섹션 9: 스프링 AOP 개념

---

## AOP가 뭔데?

**Aspect Oriented Programming** = 관점 지향 프로그래밍

## 핵심 기능 vs 부가 기능

- **핵심 기능**: 객체의 고유 기능 (주문 로직 등)
- **부가 기능**: 핵심 기능을 보조 (로그, 트랜잭션 등) — 여러 곳에 분산, 중복 증가

로그, 트랜잭션, 보안 체크 같은 부가 기능이 수십 개 클래스에 흩어져 있음. 하나 바꾸려면 전부 수정해야 함. 이렇게 여러 클래스를 가로지르며 반복되는 관심사를 **횡단 관심사(cross-cutting concerns)** 라고 함.

> AOP는 OOP를 대체하는 것이 아니라, OOP만으로는 깔끔하게 처리하기 어려운 횡단 관심사를 보조하는 것.

**AOP의 해결**: 흩어진 부가 기능을 **한 곳에 모아서(Aspect)** 관리하고, "어디에 적용할지"만 지정하면 자동 적용.

> **비유**:
> - 기존 방식: 아파트 100세대에 직접 돌아다니며 소독 (100번 반복)
> - AOP 방식: "방역 업체(Aspect)에 '5층 이상 전부(포인트컷)' 소독해달라고 의뢰" (한 번만 설정)

## 애스펙트 (Aspect)

부가 기능 + 적용 대상을 함께 정의한 모듈. "로그 출력 기능을 모든 컨트롤러에 적용"

## AOP 적용 방식

| 시점 | 방식 | 특징 |
|------|------|------|
| 컴파일 시점 | AspectJ 컴파일러 | 특별한 컴파일러 필요 |
| 클래스 로딩 시점 | 로드 타임 위빙 | java -javaagent 필요 |
| **런타임 시점** | **프록시 기반 (스프링 AOP)** | **스프링 빈에만 적용, 메서드 실행 지점만** |

### 왜 런타임 프록시 방식을 쓸까?

프록시 방식은 메서드 실행 지점에만 AOP를 적용할 수 있지만(오버라이딩 개념이므로 생성자, static 메서드, 필드 접근 불가), **실무에서 이 제약이 문제가 되는 경우는 거의 없음**. 반면 컴파일 시점/클래스 로딩 시점 방식은 특별한 컴파일러(AspectJ)나 java-agent를 관리해야 해서 운영이 까다로움.

## AOP 용어 정리

| 용어 | 설명 | 쉬운 설명 |
|------|------|-----------|
| 조인 포인트 | AOP 적용 가능 지점 (스프링에선 메서드 실행만) | AOP를 끼워 넣을 수 있는 지점 |
| 포인트컷 | 어디에 적용할지 선별 | "어디에 적용?" 필터 조건 |
| 타켓 | 부가 기능을 받는 실제 객체 | 부가 기능이 적용되는 진짜 객체 |
| 어드바이스 | 실제 부가 기능 로직 | "뭘 할 건데?" 실제 부가 기능 코드 |
| 애스펙트 | 어드바이스 + 포인트컷의 결합 | 포인트컷 + 어드바이스를 묶은 모듈 (@Aspect 클래스) |
| 어드바이저 | 하나의 어드바이스 + 하나의 포인트컷 | - |
| 위빙 | 어드바이스를 타켓에 적용하는 과정 | 어드바이스를 타켓에 연결하는 과정 |
