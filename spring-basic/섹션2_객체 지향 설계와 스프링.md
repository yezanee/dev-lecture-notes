# 섹션2. 객체 지향 설계와 스프링

### 1. 자바 진영의 겨울: EJB의 시대

2000년대 초반 자바 진영의 표준 기술은 **EJB(Enterprise Java Beans)** 였다. EJB는 트랜잭션 관리, 분산 기술, ORM(엔티티 빈) 등을 포괄하는 종합 기술 스택으로, IBM WebSphere·Oracle WebLogic 등이 J2EE 표준을 구현한 서버를 수천만 원에 판매했다. 그러나 EJB는 인터페이스 의존적 설계 강제, 복잡한 설정, 느린 컨테이너 기동, 지저분한 코드 등 심각한 실용성 문제를 안고 있었고, 개발자들 사이에서 "순수한 자바로 돌아가자"는 의미의 **POJO(Plain Old Java Object)** 운동이 등장할 정도였다.

- **EJB의 장점:** 선언적 트랜잭션 관리, 분산 컴퓨팅 지원, 엔티티 빈(ORM 기능), 자바 진영 공식 표준
- **EJB의 단점:** 대당 수천만 원의 서버 비용, 복잡하고 느린 컨테이너, EJB 인터페이스 강제 상속으로 인한 코드 오염, 테스트 어려움
- **EJB 엔티티 빈(ORM):** 조인 등 복잡한 쿼리 처리가 사실상 불가능한 수준으로 기술 완성도가 낮았음
- **POJO 운동:** EJB 종속 코드에서 벗어나 순수 자바 객체 지향 개발로 회귀하자는 흐름

### 2. 스프링과 하이버네이트의 탄생

EJB에 좌절한 두 개발자가 독립적으로 오픈소스를 창시했다. **로드 존슨(Rod Johnson)** 은 2002년 EJB의 문제점을 비판하는 책을 출간하며 3만 줄 이상의 예제 코드를 공개했고, 이 코드 안에 BeanFactory·ApplicationContext·의존관계 주입(DI)·제어의 역전(IoC) 등 스프링의 핵심 개념이 모두 담겨 있었다. **개빈 킹(Gavin King)** 은 EJB 엔티티 빈의 한계에 분노해 퇴근 후 **하이버네이트(Hibernate)** 를 개발했다.

- **스프링 명명:** 얀 카로프(Juergen Hoeller의 동료)가 EJB라는 "겨울"을 넘어선 "새로운 봄"이라는 의미로 Spring 명명
- **스프링 공동 창시:** 유겐 힐러(Juergen Hoeller)와 얀 카로프가 로드 존슨에게 오픈소스 프로젝트 제안 → 스프링 프레임워크 탄생, 유겐 힐러는 현재도 핵심 코드 대부분을 개발 중
- **하이버네이트의 성공:** EJB 3.0의 공식 ORM 대신 하이버네이트가 시장을 장악 → JCP가 개빈 킹을 영입해 하이버네이트를 기반으로 **JPA(Java Persistence API)** 표준 제정
- **JPA 현황:** 자바 ORM 시장의 약 90% 점유, 구현체 기준 하이버네이트가 80% 이상 차지
- **JPA 성공 요인:** 현장 개발자가 만든 실용성(하이버네이트) + 표준화 과정의 정제(JCP) 결합

### 3. 스프링의 역사와 스프링 부트

스프링 프레임워크는 초기 XML 기반 설정에서 출발해 버전을 거듭하며 발전했다. 2014년 **스프링 부트 1.0** 출시는 설정 복잡성과 배포 불편함을 획기적으로 해소한 전환점이었다.

- **버전별 주요 변화:**
  - 1.0: XML 기반 설정
  - 2.0: XML 설정 편의 기능 강화
  - 3.0: 자바 코드 기반 설정 공식 지원
  - 4.0: Java 8 지원
  - 2014년: 스프링 부트 출시
  - 2017년: 스프링 5(WebFlux) — 리액티브 프로그래밍(논블로킹·비동기, Node.js 유사 방식) 지원
- **스프링 부트의 핵심 장점:**
  - 톰캣 등 웹 서버 내장 → 별도 설치·배포 불필요, `java -jar`로 즉시 실행
  - 스타터 종속성(spring-boot-starter-*)으로 관련 라이브러리 일괄 관리
  - 외부 라이브러리 버전 호환성 자동 관리 (스프링이 직접 테스트·지정)
  - 메트릭·모니터링 등 프로덕션 준비 기능 기본 제공
  - 관례 기반 자동 설정(Convention over Configuration)
- **주의:** 스프링 부트는 스프링 프레임워크와 독립적으로 동작하지 않음! 스프링 프레임워크를 편리하게 사용하도록 돕는 도구

### 4. 스프링의 핵심 컨셉: 객체 지향과 다형성

스프링의 본질은 "좋은 객체 지향 애플리케이션을 개발할 수 있도록 돕는 프레임워크"이다. 자바의 가장 강력한 특징인 객체 지향, 그 중에서도 **다형성(Polymorphism)** 을 극대화하는 것이 스프링의 존재 이유다.

- **역할과 구현의 분리 원칙:**
  - 역할 = 인터페이스, 구현 = 인터페이스를 구현한 클래스/객체
  - 클라이언트는 인터페이스(역할)만 알면 됨 → 구현 내부 구조·변경에 영향받지 않음
  - 구현 대상을 무한히 확장 가능 (전기차가 나와도 운전면허 재취득 불필요)
- **다형성의 본질:** 인터페이스를 구현한 객체 인스턴스를 **실행 시점에 유연하게 변경** 가능. 클라이언트를 변경하지 않고 서버 구현 기능을 교체하는 것
- **자바에서의 구현:** 오버라이딩(Overriding)을 통해 실현. `MemberRepository` 인터페이스에 `MemoryMemberRepository` 또는 `JdbcMemberRepository`를 런타임에 주입
- **설계 원칙:** 인터페이스를 먼저 설계하고 구현체를 나중에 결정. 인터페이스 자체가 변경되면 클라이언트·서버 모두 대규모 수정 필요 → 인터페이스를 안정적으로 설계하는 것이 최우선
- **스프링과의 연결:** IoC·DI는 다형성을 활용해 역할과 구현을 편리하게 다룰 수 있도록 지원하는 기능. 스프링 컨테이너가 레고 블록 조립처럼 구현체 교체를 가능하게 함

### 5. SOLID 원칙 

클린 코드로 유명한 **로버트 마틴(Robert Martin)** 이 정리한 객체 지향 설계 5원칙으로, 다형성만으로는 해결되지 않는 설계 문제를 보완한다.

- **SRP (단일 책임 원칙):**
  - 하나의 클래스는 하나의 책임만 가져야 함
  - 변경 시 파급 효과가 최소화되면 잘 지킨 것
  - 뷰 변경 시 SQL까지 수정해야 하는 구조는 위반 사례
- **OCP (개방-폐쇄 원칙) ★가장 중요★:**
  - 확장에는 열려 있고 변경에는 닫혀 있어야 함
  - 인터페이스를 구현한 새 클래스를 추가하는 것은 기존 코드 변경이 아님
  - **문제점:** `MemberService`가 `new MemoryMemberRepository()`처럼 구현체를 직접 선택하면 교체 시 클라이언트 코드 수정 불가피 → OCP 위반
  - **해결책:** 객체 생성·관계 설정을 담당하는 별도 설정자(스프링 컨테이너) 필요
- **LSP (리스코프 치환 원칙):**
  - 하위 타입은 상위 타입의 규약을 반드시 준수해야 함
  - 자동차 인터페이스의 액셀 기능이 "앞으로 가기"라면 구현체가 뒤로 가도록 만들면 LSP 위반 (컴파일 오류 없어도 위반)
- **ISP (인터페이스 분리 원칙):**
  - 하나의 큰 인터페이스보다 특정 클라이언트를 위한 여러 작은 인터페이스가 나음
  - 자동차 인터페이스 → 운전 인터페이스 + 정비 인터페이스로 분리 시 정비 변경이 운전자 클라이언트에 영향 없음
  - 스프링 프레임워크 내부 코드는 ISP를 철저히 준수
- **DIP (의존관계 역전 원칙) ★OCP와 함께 핵심★:**
  - 추상화(인터페이스)에 의존해야 하며 구체화(구현 클래스)에 의존하면 안 됨
  - `MemberService`가 `MemberRepository` 인터페이스와 `MemoryMemberRepository` 구현체를 동시에 알고 있으면 DIP 위반
  - **결론:** 다형성만으로는 OCP·DIP를 동시에 지킬 수 없으며, 이를 해결하기 위해 DI 컨테이너(스프링)가 필요

### 이번 강의의 핵심 포인트

- **스프링의 본질은 객체 지향이다:** 스프링은 단순한 웹 프레임워크가 아니라, 자바의 다형성을 극대화해 좋은 객체 지향 애플리케이션을 만들 수 있도록 돕는 도구이며, 이 핵심 컨셉을 모르면 스프링을 제대로 이해할 수 없다.
- **역할과 구현의 분리가 유연성의 근원이다:** 인터페이스(역할)와 구현체를 철저히 분리해야 클라이언트 코드 변경 없이 기능을 확장·교체할 수 있으며, 인터페이스를 안정적으로 설계하는 것이 가장 중요한 설계 역량이다.
- **다형성만으로는 부족하다—스프링 컨테이너가 필요한 이유:** OCP와 DIP를 동시에 지키려면 객체 생성과 의존관계 연결을 담당하는 별도의 설정자가 필요하고, 그것이 바로 스프링 DI 컨테이너다.
- **단순 API 사용법이 아닌 핵심 컨셉을 이해하라**
