# 섹션4. 스프링 핵심 원리의 이해 2

### 1. 새로운 할인 정책 개발

기획 요구사항이 변경되어 고정 금액 할인(정액)에서 주문 금액의 10%를 할인하는 정률 방식으로 전환해야 한다. 처음부터 인터페이스 기반으로 설계했으므로, 새로운 구현체를 추가하는 것 자체는 어렵지 않다.

- RateDiscountPolicy (구현체): VIP이면 주문 금액의 10% 할인, 그 외 0원 반환
  ```java
  public class RateDiscountPolicy implements DiscountPolicy {

      private int discountPercent = 10;

      @Override
      public int discount(Member member, int price) {
          if (member.getGrade() == Grade.VIP) {
              return price * discountPercent / 100;
          } else {
              return 0;
          }
      }
  }
  ```
- 테스트: `@DisplayName`으로 테스트 의도를 명확히 드러내는 습관이 중요하다.
  ```java
  class RateDiscountPolicyTest {

      RateDiscountPolicy discountPolicy = new RateDiscountPolicy();

      @Test
      @DisplayName("VIP는 10% 할인이 적용되어야 한다.")
      void vip_o() {
          Member member = new Member(1L, "memberVIP", Grade.VIP);
          int discount = discountPolicy.discount(member, 10000);
          assertThat(discount).isEqualTo(1000);
      }

      @Test
      @DisplayName("VIP가 아니면 할인이 적용되지 않아야 한다.")
      void vip_x() {
          Member member = new Member(2L, "memberBASIC", Grade.BASIC);
          int discount = discountPolicy.discount(member, 10000);
          assertThat(discount).isEqualTo(0);
      }
  }
  ```

### 2. 새로운 할인 정책 적용과 문제점

새 정책을 적용하려면 `OrderServiceImpl`에서 할인 정책 구현체를 직접 변경해야 한다.

```java
public class OrderServiceImpl implements OrderService {
    // private final DiscountPolicy discountPolicy = new FixDiscountPolicy();
    private final DiscountPolicy discountPolicy = new RateDiscountPolicy(); // 변경!
}
```

동작은 하지만, 이 코드에는 두 가지 설계 원칙 위반이 존재한다.

- **DIP 위반:** `OrderServiceImpl`은 `DiscountPolicy` 인터페이스(추상)뿐만 아니라 `FixDiscountPolicy`·`RateDiscountPolicy` 구체 클래스에도 동시에 의존한다. 클래스 다이어그램에서 `OrderServiceImpl` → 구체 클래스로 직접 향하는 화살표가 존재하는 구조이며, "추상화에 의존해야지 구체화에 의존하면 안 된다"는 DIP에 명백히 위반된다.
- **OCP 위반:** 할인 정책을 `RateDiscountPolicy`로 교체하려면 `OrderServiceImpl`의 소스 코드를 직접 수정해야 한다. 기능 확장(새로운 정책 추가)이 클라이언트 코드의 변경을 유발하므로 "확장에는 열려 있고 변경에는 닫혀 있어야 한다"는 OCP를 위반한다.
- **근본 원인:** `OrderServiceImpl`이 주문 로직 실행과 사용할 할인 정책 구현체 선택(생성)이라는 두 가지 역할을 동시에 맡고 있기 때문이다. 배우가 공연도 하면서 상대 배역까지 직접 섭외하는 상황에 비유할 수 있다.

### 3. 관심사의 분리 — AppConfig 등장

"구현 객체를 생성하고 연결하는 책임"을 별도의 클래스로 분리해야 한다. 공연에서 배역에 맞는 배우를 섭외하고 무대를 구성하는 "공연 기획자" 역할을 `AppConfig`가 담당한다.

- AppConfig: 구현 객체를 생성하고, 생성자를 통해 주입(DI)하는 역할을 전담한다.
  ```java
  public class AppConfig {

      public MemberService memberService() {
          return new MemberServiceImpl(new MemoryMemberRepository());
      }

      public OrderService orderService() {
          return new OrderServiceImpl(
                  new MemoryMemberRepository(),
                  new FixDiscountPolicy());
      }
  }
  ```
- MemberServiceImpl: 생성자를 통해 `MemberRepository` 구현체를 외부에서 주입받는다.
  ```java
  public class MemberServiceImpl implements MemberService {

      private final MemberRepository memberRepository;

      public MemberServiceImpl(MemberRepository memberRepository) {
          this.memberRepository = memberRepository;
      }
      // ...
  }
  ```
- OrderServiceImpl: 생성자를 통해 `MemberRepository`와 `DiscountPolicy` 구현체를 외부에서 주입받는다. 어떤 구현체가 들어올지는 전혀 모르며, 오직 `AppConfig`만이 알고 있다.
  ```java
  public class OrderServiceImpl implements OrderService {

      private final MemberRepository memberRepository;
      private final DiscountPolicy discountPolicy;

      public OrderServiceImpl(MemberRepository memberRepository, DiscountPolicy discountPolicy) {
          this.memberRepository = memberRepository;
          this.discountPolicy = discountPolicy;
      }
      // ...
  }
  ```
- 핵심 변화: 각 구현체는 인터페이스에만 의존하며, 클라이언트가 수동적으로 의존관계를 주입받는 이 구조를 **DI(Dependency Injection, 의존관계 주입)** 라고 한다.

### 4. AppConfig 리팩터링

초기 `AppConfig`에는 `new MemoryMemberRepository()`가 두 군데 중복되어 있으며, 어떤 역할에 어떤 구현체를 사용하는지 한눈에 들어오지 않는다. 역할과 구현이 명확하게 보이도록 리팩터링한다.

```java
public class AppConfig {

    public MemberService memberService() {
        return new MemberServiceImpl(memberRepository());
    }

    public OrderService orderService() {
        return new OrderServiceImpl(memberRepository(), discountPolicy());
    }

    public MemberRepository memberRepository() {
        return new MemoryMemberRepository();
    }

    public DiscountPolicy discountPolicy() {
        return new FixDiscountPolicy();
    }
}
```

- `AppConfig`만 보면 "회원 저장소는 메모리 구현체, 할인 정책은 정액 구현체"라는 전체 구성이 한눈에 파악 가능하다.
- `MemoryMemberRepository`를 다른 구현체로 교체할 때도 `memberRepository()` 한 곳만 수정하면 된다.

### 5. 새로운 구조와 할인 정책 적용

리팩터링된 구조에서 정률 할인으로 정책을 변경하려면 `AppConfig`의 구성 영역 한 곳만 변경하면 된다.

```java
public DiscountPolicy discountPolicy() {
    // return new FixDiscountPolicy();
    return new RateDiscountPolicy(); // 이 한 줄만 변경
}
```

- `OrderServiceImpl`을 비롯한 사용 영역의 코드는 단 한 줄도 수정하지 않는다.
- 애플리케이션이 **사용 영역**과 **구성(Configuration) 영역**으로 명확하게 분리되었기 때문에 가능한 구조이다.
- SOLID 원칙 적용 결과:
  - **SRP(단일 책임 원칙):** 기존에는 클라이언트 객체가 생성·연결·실행 책임을 모두 지고 있었으나, AppConfig가 생성·연결 책임을, 각 구현체가 실행 책임을 분담하게 되었다.
  - **DIP(의존관계 역전 원칙):** 클라이언트 코드가 추상 인터페이스에만 의존하며, `AppConfig`가 구체 클래스 인스턴스를 생성해서 주입해준다.
  - **OCP(개방-폐쇄 원칙):** 할인 정책을 변경해도 사용 영역의 코드는 전혀 수정할 필요가 없다. 확장은 열려 있고 변경은 닫혀 있다.

### 6. IoC, DI, 그리고 컨테이너

- **제어의 역전(IoC, Inversion of Control):** 기존에는 구현 객체가 스스로 필요한 객체를 생성하고 제어 흐름을 직접 관리했다. `AppConfig` 등장 이후 구현 객체는 자신의 로직 실행에만 집중하고, 프로그램의 제어 흐름은 `AppConfig`가 가져간다. 이처럼 제어 흐름을 외부에서 관리하는 것을 제어의 역전(IoC)이라 한다.
  - 프레임워크: 내가 작성한 코드를 프레임워크가 제어하고 대신 실행 (예: JUnit)
  - 라이브러리: 내가 작성한 코드가 직접 제어 흐름을 담당
- **의존관계 주입(DI, Dependency Injection):** 의존관계는 정적인 클래스 의존관계와 동적인 객체 인스턴스 의존관계로 구분한다.
  - 정적인 클래스 의존관계: import 코드만으로 파악 가능하며, 애플리케이션을 실행하지 않아도 분석할 수 있다. 다만 실제로 어떤 구현체가 주입될지는 알 수 없다.
  - 동적인 객체 인스턴스 의존관계: 실행 시점(런타임)에 외부에서 실제 구현 객체를 생성하고 클라이언트에 전달하여 실제 의존관계가 연결되는 것이다. 이것이 바로 의존관계 주입(DI)이다.
  - DI를 사용하면 정적인 클래스 의존관계를 변경하지 않고도 동적인 객체 인스턴스 의존관계를 자유롭게 변경할 수 있다.
- **IoC/DI 컨테이너:** `AppConfig`처럼 객체를 생성·관리하면서 의존관계를 연결해주는 것을 IoC 컨테이너 또는 DI 컨테이너라 한다. 최근에는 의존관계 주입에 초점을 맞춰 주로 DI 컨테이너라고 부른다.

### 7. 스프링으로 전환하기

순수 자바 코드로 구현한 DI를 스프링 컨테이너로 전환한다. `AppConfig`에 `@Configuration`과 `@Bean` 애노테이션을 추가하면 된다.

```java
@Configuration
public class AppConfig {

    @Bean
    public MemberService memberService() {
        return new MemberServiceImpl(memberRepository());
    }

    @Bean
    public OrderService orderService() {
        return new OrderServiceImpl(memberRepository(), discountPolicy());
    }

    @Bean
    public MemberRepository memberRepository() {
        return new MemoryMemberRepository();
    }

    @Bean
    public DiscountPolicy discountPolicy() {
        return new RateDiscountPolicy();
    }
}
```

- `@Configuration`: 해당 클래스가 스프링 설정 정보임을 알려준다.
- `@Bean`: 해당 메서드가 반환하는 객체를 스프링 컨테이너에 스프링 빈으로 등록한다. 빈 이름은 기본적으로 메서드 이름을 사용한다.
- 사용 측: `AppConfig`를 직접 사용하는 대신 `ApplicationContext`(스프링 컨테이너)를 통해 빈을 조회한다.
  ```java
  ApplicationContext applicationContext =
          new AnnotationConfigApplicationContext(AppConfig.class);

  MemberService memberService =
          applicationContext.getBean("memberService", MemberService.class);
  ```
- 스프링 컨테이너는 `@Configuration`이 붙은 `AppConfig`를 설정 정보로 사용하고, `@Bean`이 붙은 메서드를 모두 호출하여 반환된 객체를 스프링 빈으로 등록한다.
- 스프링 컨테이너를 사용하면 어떤 장점이 있는지는 이후 강의에서 다룬다.

### 이번 강의의 핵심 포인트

- 다형성만으로는 OCP·DIP를 동시에 지킬 수 없다. 인터페이스 기반 설계만으로는 구체 클래스 변경 시 클라이언트 코드 수정이 불가피하며, 구현 객체의 생성과 연결을 별도로 분리해야 비로소 OCP·DIP가 지켜진다.
- AppConfig가 관심사의 분리를 실현한다. 구성 영역(AppConfig)과 사용 영역(각 구현체)을 명확히 분리함으로써 SRP·DIP·OCP를 모두 충족하는 구조가 완성되며, 정책 변경 시 구성 영역의 한 줄만 수정하면 된다.
- 스프링 컨테이너는 AppConfig의 역할을 대신한다. `@Configuration`과 `@Bean` 애노테이션을 통해 순수 자바 DI를 스프링 컨테이너 기반 DI로 전환할 수 있으며, 스프링은 이 IoC/DI 컨테이너 역할을 보다 체계적으로 수행한다.
