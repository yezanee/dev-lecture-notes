# 섹션 10: 모니터링 메트릭 활용

## 1. 커스텀 메트릭이 필요한 이유

CPU, 메모리, 톰캣 쓰레드, DB 커넥션 풀 같은 **공통 메트릭**은 이미 자동으로 등록되어 있다. 하지만 **비즈니스에 특화된 메트릭**은 직접 등록해야 한다.

예시:
- **주문 수**: 주문하면 증가
- **취소 수**: 취소하면 증가 (주문 수는 유지)
- **재고 수량**: 주문 시 감소, 취소 시 증가, 입고 시 증가

## 2. MeterRegistry

마이크로미터 기능을 제공하는 **핵심 컴포넌트**. 스프링을 통해 주입받아 카운터, 게이지 등을 등록한다.

> 메트릭은 약간의 오차가 존재할 수 있다. 실시간 데이터를 **대략적으로 보는 것**이 목적이다.

## 3. 카운터 (Counter)

### 특징
- **단조롭게 증가하는** 단일 누적 측정항목
- 값을 증가하거나 0으로 초기화하는 것만 가능
- 프로메테우스에서는 이름 끝에 `_total`이 자동으로 붙음 (예: `my_order_total`)

### 직접 등록 방식

```java
public class OrderServiceV1 implements OrderService {
    private final MeterRegistry meterRegistry;

    @Override
    public void order() {
        log.info("주문");
        stock.decrementAndGet();

        Counter.builder("my.order")
            .tag("class", this.getClass().getName())
            .tag("method", "order")
            .description("order")
            .register(meterRegistry)
            .increment();  // 카운터 증가
    }

    @Override
    public void cancel() {
        log.info("취소");
        stock.incrementAndGet();

        Counter.builder("my.order")
            .tag("class", this.getClass().getName())
            .tag("method", "cancel")
            .description("order")
            .register(meterRegistry)
            .increment();
    }
}
```

**메트릭 확인:**

`GET http://localhost:8081/actuator/metrics/my.order`
```json
{
  "name": "my.order",
  "measurements": [{ "statistic": "COUNT", "value": 1.0 }],
  "availableTags": [
    { "tag": "method", "values": ["order", "cancel"] },
    { "tag": "class", "values": ["...OrderServiceV1"] }
  ]
}
```

**프로메테우스 포맷:**
```
my_order_total{class="...OrderServiceV1", method="order"} 1.0
```

### @Counted (AOP 방식) — 더 간편!

메서드에 `@Counted` 어노테이션만 붙이면 자동으로 카운터 메트릭이 등록된다:

```java
@Service
public class OrderServiceV2 implements OrderService {

    @Counted("my.order")
    @Override
    public void order() {
        log.info("주문");
        stock.decrementAndGet();
    }

    @Counted("my.order")
    @Override
    public void cancel() {
        log.info("취소");
        stock.incrementAndGet();
    }
}
```

**⚠️ 중요: `CountedAspect` 빈을 반드시 등록해야 `@Counted` AOP가 동작한다!**

```java
@Configuration
public class OrderConfigV2 {
    @Bean
    public CountedAspect countedAspect(MeterRegistry registry) {
        return new CountedAspect(registry);
    }
}
```

## 4. 타이머 (Timer)

### 특징

시간을 측정하는 특별한 메트릭 도구. 카운터와 유사하지만 **실행 시간도 함께 측정**:

| 측정 항목 | 의미 | 프로메테우스 타입 |
|----------|------|----------------|
| `seconds_count` | 누적 실행 수 | counter |
| `seconds_sum` | 실행 시간의 합 | sum |
| `seconds_max` | 최대 실행 시간 | gauge |

- `seconds_sum / seconds_count` = **평균 실행 시간** (계산으로 구함)
- `seconds_max`는 내부에 **타임 윈도우**가 있어서 1~3분마다 다시 계산됨

### 직접 등록 방식

```java
public class OrderServiceV3 implements OrderService {
    private final MeterRegistry meterRegistry;

    @Override
    public void order() {
        Timer timer = Timer.builder("my.order")
            .tag("class", this.getClass().getName())
            .tag("method", "order")
            .description("order")
            .register(meterRegistry);

        timer.record(() -> {
            log.info("주문");
            stock.decrementAndGet();
        });
    }
}
```

### @Timed (AOP 방식) — 더 간편!

```java
@Service
@Timed("my.order")  // 클래스 레벨에 적용하면 모든 public 메서드에 적용
public class OrderServiceV4 implements OrderService {
    // ...
}
```

**⚠️ `TimedAspect` 빈을 반드시 등록해야 한다!**

```java
@Bean
public TimedAspect timedAspect(MeterRegistry registry) {
    return new TimedAspect(registry);
}
```

## 5. 게이지 (Gauge)

### 특징

- 임의로 **오르내릴 수 있는** 단일 숫자 값
- **현재 상태**를 보는 데 사용
- 예: 차량 속도, CPU 사용량, 메모리 사용량, **재고 수량**

> **카운터 vs 게이지 구분법:** 값이 감소할 수 있는가? → 감소 가능하면 게이지, 증가만 하면 카운터

### 등록 방법

```java
@Configuration
public class MyStockConfigV2 {

    @Bean
    public MeterBinder stockSize(OrderService orderService) {
        return registry -> Gauge.builder("my.stock", () -> 
            orderService.getStock().get()
        ).register(registry);
    }
}
```

게이지는 값을 설정하는 것이 아니라, **값을 조회하는 함수를 등록**한다. 프로메테우스가 메트릭을 수집할 때마다 이 함수가 호출되어 현재 값을 반환한다.

## 6. 실무 모니터링 환경 구성 팁

### 모니터링 3단계

```
넓음  ←─────────────────────────────────────→  좁음
대시보드          애플리케이션 추적           로그
(전체 한눈에)      (요청 하나하나)         (가장 상세)
```

### 1단계: 대시보드

전체 시스템을 **한눈에** 볼 수 있는 가장 높은 뷰

**제품:** 마이크로미터 + 프로메테우스 + 그라파나

**모니터링 대상:**
- 시스템 메트릭: CPU, 메모리
- 애플리케이션 메트릭: 톰캣 쓰레드 풀, DB 커넥션 풀, 애플리케이션 호출 수
- 비즈니스 메트릭: 주문 수, 취소 수

### 2단계: 애플리케이션 추적

각각의 **HTTP 요청을 하나하나 추적**. 마이크로서비스 환경에서는 분산 추적이 중요.

**제품:**
- **핀포인트 (Pinpoint)** — 오픈소스, 강력 추천 ⭐
- 스카우트 — 오픈소스
- 와탭 — 상용
- 제니퍼 — 상용

> 핀포인트는 마이크로서비스 분산 모니터링이 가능하고, 대용량 트래픽에도 대응 가능한 매우 좋은 도구이다.

### 3단계: 로그

가장 **자세한 추적**, 원하는 대로 커스텀 가능

**핵심: 같은 HTTP 요청을 묶어서 확인할 수 있어야 한다!**
- 고객 요청이 들어올 때 UUID 같은 것을 생성하여 로그에 함께 남기기
- **MDC(Mapped Diagnostic Context)** 적용

**파일로 로그를 남기는 경우:**
- **일반 로그와 에러 로그는 파일을 구분**해서 남기자
- 에러 로그만 별도로 확인하면 문제를 빠르게 정리할 수 있음

**클라우드에 로그를 저장하는 경우:**
- 검색이 잘 되도록 구분하자

### 알람 설정

모니터링 툴에서 일정 수치를 넘어가면 슬랙, 문자 등으로 연동

**⚠️ 알람은 반드시 2가지로 구분하여 관리:**

| 구분 | 기준 | 대응 | 예시 |
|------|------|------|------|
| **경고** | 하루 1번 정도 확인해도 되는 수준 | 사람이 직접 확인 | 디스크 70%, CPU 40% |
| **심각** | 즉시 확인 필요 | 슬랙 알림, 문자, 전화 | 디스크 80%, CPU 50% |

> **거짓(False) 알람은 바로바로 처리하자.** 늑대가 나타났다 이야기처럼 거짓 알람이 많으면 진짜 알람을 무시하게 된다.
