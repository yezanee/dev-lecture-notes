# 섹션 1: 스프링 부트 소개

## 1. 스프링 프레임워크의 등장 배경

### EJB(Enterprise Java Beans)의 문제점

과거 자바 진영의 표준 기술은 **EJB**였다. 이론적으로는 잘 설계되어 있었지만 실무에서는 심각한 문제가 있었다.

- **높은 복잡성**: 공부하기 너무 어려웠고, EJB 인터페이스 구현이 까다로웠다
- **높은 의존성**: EJB에 의존적으로 개발해야 했다 (코드가 EJB에 종속됨)
- **높은 가격**: EJB 컨테이너(WAS)가 매우 비쌌다
- 이런 문제들 때문에 **POJO(Plain Old Java Object)** — 순수한 자바를 사용하자는 움직임이 생겨났다

### 스프링의 탄생

2002년, **로드 존슨(Rod Johnson)**이 *"J2EE Design and Development"*라는 책을 출간한다.

- EJB의 문제점을 지적하고, EJB 없이도 고품질의 확장 가능한 애플리케이션을 개발할 수 있음을 **30,000줄 이상의 예제 코드**로 증명
- 이 책에 스프링의 핵심 개념과 기반 코드가 포함되어 있었다
  - **BeanFactory**, **ApplicationContext**, **POJO**, **제어의 역전(IoC)**, **의존관계 주입(DI)**
- 이 책이 유명해지면서 개발자들이 예제 코드를 실제 프로젝트에 사용하기 시작했고, 결국 오픈소스 프로젝트 **스프링 프레임워크**로 발전했다

### 스프링의 주요 역사

| 년도 | 버전 | 특징 |
|------|------|------|
| 2003 | Spring Framework 1.0 | XML 설정 |
| 2006 | Spring Framework 2.0 | XML 편의 기능 지원 |
| 2009 | Spring Framework 3.0 | 자바 코드로 설정 가능 |
| 2013 | Spring Framework 4.0 | 자바 8 지원 |
| 2014 | **Spring Boot 1.0** | 스프링 부트 등장 |
| 2017 | Spring Framework 5.0 / Boot 2.0 | 리액티브 프로그래밍 지원 |
| 2022 | Spring Framework 6.0 / Boot 3.0 | 자바 17 필수, Jakarta EE |

## 2. 스프링 프레임워크

### 스프링이 제공하는 것들

- **핵심 기술**: DI 컨테이너, AOP, 이벤트
- **웹 기술**: Spring MVC, Spring WebFlux
- **데이터 접근 기술**: 트랜잭션, JDBC, ORM 지원
- **기술 통합**: 캐시, 이메일, 원격접근, 스케줄링
- **테스트**: 스프링 기반 테스트 지원

### 스프링 기반 생태계

스프링 프레임워크를 중심으로 거대한 생태계가 형성되었다:

- Spring Framework (핵심)
- Spring Data (데이터 접근 추상화)
- Spring Session (세션 관리)
- Spring Security (보안)
- Spring REST Docs (API 문서화)
- Spring Batch (대용량 배치 처리)
- Spring Cloud (마이크로서비스)

### 스프링 프레임워크의 한계 — "설정 지옥"

스프링이 성장하면서 오히려 사용하기 어려워지는 문제가 발생했다:

1. **스프링 설정 지옥**: 프로젝트를 시작하려면 엄청나게 많은 설정을 알아야 했다
2. **빈 등록 지옥**: 늘어난 라이브러리의 빈을 일일이 등록해야 했다
3. **라이브러리 버전 호환성 문제**: 수많은 라이브러리의 버전 호환을 직접 맞춰야 했다

> 시작도 하기 전에 복잡한 설정 때문에 포기하는 경우가 빈번했다.

## 3. 스프링 부트의 등장

### BOOT의 의미

**Boot(부팅)** = 최소한의 인간 개입으로 시작하고 완전히 작동하는 것

스프링 부트는 스프링으로 프로젝트를 시작하기 위한 복잡한 설정 과정을 대신 해결해준다.

### 스프링 부트 핵심 기능 5가지

| 기능 | 설명 | 해결하는 문제 |
|------|------|-------------|
| **1. 내장 WAS** | Tomcat 같은 웹 서버를 내장 | 별도 WAS 설치 불필요 |
| **2. 라이브러리 관리** | 스타터 종속성 제공 + 버전 자동 관리 | 라이브러리 선택/호환성 고민 해소 |
| **3. 자동 구성** | 필요한 빈을 자동으로 등록 | 빈 등록 지옥 해소 |
| **4. 외부 설정** | 환경별 설정을 공통화 | 환경별 빌드 문제 해소 |
| **5. 프로덕션 준비** | 메트릭, 상태 확인 기능 제공 | 모니터링 구축 부담 감소 |

### 핵심: 스프링 부트 ≠ 새로운 프레임워크

> **스프링 부트는 스프링 프레임워크를 쉽게 사용할 수 있게 도와주는 도구일 뿐이다. 본질은 스프링 프레임워크다.**

하지만 스프링 부트가 제공하는 편의 기능이 너무 막강해서 사실상 스프링 부트 사용은 필수가 되었다.

## 4. 스프링 부트를 배워야 하는 이유

1. **너무 많은 자동화의 함정**: 편리하지만 내부 원리를 모르면 문제 발생 시 해결할 수 없다
2. **문제 해결 능력**: 최소한 스프링 부트가 어떤 원리로 작동하는지 알아야 문제 파악이 가능하다
3. **편의 기능 활용**: 외부 설정, 액츄에이터 등 이미 만들어진 기능을 알면 불필요한 개발을 피할 수 있다
4. **개발 시간 단축**: 대부분의 개발자가 비슷하게 고민하는 기능을 스프링 부트가 이미 제공한다

### "스프링"의 여러 의미

문맥에 따라 다르게 사용되니 주의:

- **스프링 DI 컨테이너** 기술 자체
- **스프링 프레임워크** (좁은 의미)
- 스프링 부트, 스프링 프레임워크 등을 모두 포함한 **스프링 생태계** (넓은 의미)
