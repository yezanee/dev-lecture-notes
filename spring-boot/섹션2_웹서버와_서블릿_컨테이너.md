# 섹션 2: 웹 서버와 서블릿 컨테이너

## 1. 웹 서버와 스프링 부트 소개

### 전통적인 방식 (외장 서버)

```
[개발자] → 코드 작성 → WAR 빌드 → WAS(톰캣)에 배포
```

1. 서버에 톰캣 같은 **WAS(웹 애플리케이션 서버)**를 별도 설치
2. WAS에서 동작하도록 **서블릿 스펙**에 맞춰 코드를 작성
3. **WAR 형식**으로 빌드하여 war 파일 생성
4. war 파일을 WAS에 전달하여 배포

이 방식은 WAS를 먼저 설치해야 하고, WAS와 연동하기 위한 **복잡한 추가 설정**이 필요했다.

### 최근 방식 (내장 서버)

```
[개발자] → 코드 작성 → JAR 빌드 → java -jar 실행 (끝!)
```

- 스프링 부트가 **내장 톰캣**을 포함하고 있다
- 애플리케이션 코드 안에 톰캣이 **라이브러리로 내장**되어 있다
- 개발자는 `main()` 메서드만 실행하면 WAS도 함께 기동된다
- WAS 설치나 IDE-WAS 연동 같은 복잡한 작업이 사라졌다

> 그렇다면 스프링 부트는 어떤 원리로 내장 톰캣을 사용하여 실행할 수 있는 것일까? 이 섹션에서 그 과정을 직접 구현해보며 이해한다.

## 2. JAR와 WAR

### JAR (Java Archive)

- 자바 클래스와 리소스를 묶어 만든 **압축 파일**
- **JVM 위에서 직접 실행**되거나 라이브러리로 사용됨
- 직접 실행 시 `main()` 메서드가 필요하고, `MANIFEST.MF` 파일에 메인 클래스를 지정해야 한다
- 실행: `java -jar abc.jar`
- 핵심: **클래스와 리소스를 압축한 단순한 파일**

### WAR (Web Application Archive)

- **WAS에 배포할 때** 사용하는 파일
- JAR가 JVM 위에서 실행된다면, WAR는 **웹 애플리케이션 서버 위에서 실행**
- HTML 같은 정적 리소스와 클래스 파일을 모두 포함하여 JAR보다 구조가 복잡

**WAR 디렉토리 구조:**
```
WAR
├── WEB-INF
│   ├── classes/      ← 실행 클래스 모음
│   ├── lib/          ← 라이브러리(jar 파일) 모음
│   └── web.xml       ← 웹 서버 배치 설정 파일 (생략 가능)
└── index.html        ← 정적 리소스 (HTML, CSS 등)
```

**핵심 차이점:**
- `WEB-INF` 폴더 하위 → 자바 클래스, 라이브러리, 설정 정보
- `WEB-INF` 외부 → HTML, CSS 같은 정적 리소스

## 3. 서블릿 컨테이너 초기화

### 서블릿(Servlet)이란?

클라이언트의 요청에 맞춰 **동적인 결과를 만들어 주는 자바 웹 프로그래밍 기술**. 서블릿은 톰캣 같은 WAS의 **서블릿 컨테이너** 안에서 동작한다.

### 초기화가 필요한 이유

WAS를 실행하는 시점에 다음과 같은 초기화 작업이 필요하다:

1. 서비스에 필요한 **필터**와 **서블릿** 등록
2. 스프링을 사용한다면 **스프링 컨테이너** 생성
3. 서블릿과 스프링을 연결하는 **디스패처 서블릿(DispatcherServlet)** 등록

과거에는 `web.xml`을 사용했지만, 현재는 **자바 코드를 사용한 초기화**도 지원한다.

### 서블릿 컨테이너 초기화 (방법 1)

**`ServletContainerInitializer`** 인터페이스를 구현하는 방식:

```java
public interface ServletContainerInitializer {
    void onStartup(Set<Class<?>> c, ServletContext ctx) throws ServletException;
}
```

- `Set<Class<?>> c`: `@HandlesTypes` 어노테이션과 함께 사용하여 유연한 초기화 제공
- `ServletContext ctx`: 서블릿 컨테이너 자체의 기능 제공 (필터/서블릿 등록 등)

**등록 방법:**

`resources/META-INF/services/jakarta.servlet.ServletContainerInitializer` 파일에 구현 클래스의 전체 이름(패키지 + 클래스)을 기재한다. 톰캣이 실행될 때 이 파일을 읽어 해당 클래스의 `onStartup()` 메서드를 실행한다.

### 서블릿을 등록하는 2가지 방법

| 방법 | 장점 | 단점 |
|------|------|------|
| `@WebServlet` 어노테이션 | 간편함 | 유연한 변경 어려움 (하드코딩) |
| **프로그래밍 방식** | 유연한 변경 가능, 분기 처리 가능 | 코드가 더 많음 |

**프로그래밍 방식을 사용해야 하는 이유:**
- `@WebServlet(urlPatterns = "/test")`에서 `/test` 경로를 바꾸려면 코드를 직접 수정해야 한다
- 프로그래밍 방식은 외부 설정값으로 경로를 동적으로 변경할 수 있고, 조건에 따른 분기 처리도 가능하다

### 애플리케이션 초기화 (방법 2 — 더 유연한 방식)

`@HandlesTypes`를 활용하여 서블릿 컨테이너 초기화를 더 유연하게 만드는 방식:

```java
// 1. 애플리케이션 초기화 인터페이스 정의
public interface AppInit {
    void onStartup(ServletContext servletContext);
}

// 2. 구현체 작성
public class AppInitV1Servlet implements AppInit {
    @Override
    public void onStartup(ServletContext servletContext) {
        ServletRegistration.Dynamic helloServlet = 
            servletContext.addServlet("helloServlet", new HelloServlet());
        helloServlet.addMapping("/hello-servlet");
    }
}

// 3. 서블릿 컨테이너 초기화 클래스에서 @HandlesTypes로 연결
@HandlesTypes(AppInit.class)
public class MyContainerInitV2 implements ServletContainerInitializer {
    @Override
    public void onStartup(Set<Class<?>> c, ServletContext ctx) throws ServletException {
        // c에 AppInit 구현체들의 Class 정보가 전달됨
        for (Class<?> appInitClass : c) {
            AppInit appInit = (AppInit) appInitClass.getDeclaredConstructor().newInstance();
            appInit.onStartup(ctx);
        }
    }
}
```

**애플리케이션 초기화의 장점:**
1. **편리함**: `META-INF/services` 파일에 클래스를 추가하지 않아도 됨. 특정 인터페이스만 구현하면 자동으로 인식
2. **낮은 의존성**: 서블릿 컨테이너에 상관없이 원하는 모양으로 인터페이스를 만들 수 있어 서블릿 컨테이너에 대한 의존을 줄일 수 있음. `ServletContext`가 필요 없다면 의존을 완전히 제거할 수도 있음

## 4. 스프링 컨테이너 등록

서블릿 컨테이너 초기화와 애플리케이션 초기화를 활용하여 WAS와 스프링 컨테이너를 통합하는 과정:

### 등록 3단계

```
1. 스프링 컨테이너 생성
   └── AnnotationConfigWebApplicationContext 생성

2. 스프링 MVC 컨트롤러를 스프링 컨테이너에 빈으로 등록
   └── appContext.register(HelloConfig.class)

3. 디스패처 서블릿을 서블릿 컨테이너에 등록
   └── DispatcherServlet을 생성하고 스프링 컨테이너와 연결
```

**디스패처 서블릿(DispatcherServlet)이란?**

스프링 MVC의 핵심 컴포넌트로, HTTP 요청이 들어오면 적절한 **컨트롤러를 찾아서 호출**하는 역할을 하는 서블릿이다. 모든 요청의 진입점 역할을 한다.

> 일반적으로 스프링 컨테이너는 하나, 디스패처 서블릿도 하나만 만들고, 디스패처 서블릿 경로를 `/`로 설정하여 모든 요청을 하나의 디스패처 서블릿이 처리하도록 구성한다.

## 5. 스프링 MVC 서블릿 컨테이너 초기화 지원

위의 과정은 매우 반복적이고 번거로운 작업이다. 스프링 MVC는 이러한 서블릿 컨테이너 초기화 작업을 **이미 만들어 두었다**.

### WebApplicationInitializer

개발자는 이 인터페이스 하나만 구현하면 된다:

```java
public interface WebApplicationInitializer {
    void onStartup(ServletContext servletContext) throws ServletException;
}
```

### 내부 동작 원리

`spring-web` 라이브러리 내부를 보면:

1. `META-INF/services/jakarta.servlet.ServletContainerInitializer` 파일에 `SpringServletContainerInitializer`가 등록되어 있음
2. `SpringServletContainerInitializer`는 `@HandlesTypes(WebApplicationInitializer.class)`가 선언되어 있음
3. `onStartup()` 메서드 내부에서 `WebApplicationInitializer` 구현체들을 **리플렉션으로 생성**하여 각각 실행

```java
@HandlesTypes(WebApplicationInitializer.class)
public class SpringServletContainerInitializer implements ServletContainerInitializer {
    // WebApplicationInitializer 구현체들을 찾아서 실행
}
```

> 즉, 스프링이 서블릿 컨테이너 초기화의 복잡한 과정을 이미 구현해놓았기 때문에, 개발자는 `WebApplicationInitializer`만 구현하면 애플리케이션 초기화가 가능하다.
