# 섹션 3: 스프링 부트와 내장 톰캣

## 1. WAR 배포 방식의 단점

기존 WAR 배포 방식에는 다음과 같은 단점이 있었다:

| 단점 | 내장 톰캣으로 해결 |
|------|------------------|
| 톰캣 같은 WAS를 **별도로 설치**해야 함 | WAS가 라이브러리로 jar 내부에 포함 |
| 개발 환경 설정이 **복잡** (WAS 연동 설정) | 단순히 `main()` 메서드만 실행 |
| **배포 과정이 복잡** (WAR 빌드 → WAS 전달) | JAR를 만들고 원하는 위치에서 실행만 하면 끝 |
| 톰캣 **버전 변경 시** 톰캣을 다시 설치 | gradle에서 내장 톰캣 라이브러리 버전만 변경 후 빌드 |

> 핵심 아이디어: 자바의 `main()` 메서드만 실행시켜도 웹 서버까지 기동할 수 있을까? → **내장 톰캣(Embed Tomcat)**으로 가능!

## 2. 내장 톰캣 사용하기

### 내장 톰캣으로 서블릿 등록

톰캣을 라이브러리로 포함하고 자바 코드로 직접 실행하는 것이 내장 톰캣의 핵심이다:

```java
public class EmbedTomcatServletMain {
    public static void main(String[] args) throws LifecycleException {
        // 1. 톰캣 설정
        Tomcat tomcat = new Tomcat();
        Connector connector = new Connector();
        connector.setPort(8080);
        tomcat.setConnector(connector);

        // 2. 서블릿 등록
        Context context = tomcat.addContext("", "/");
        tomcat.addServlet("", "helloServlet", new HelloServlet());
        context.addServletMappingDecoded("/hello-servlet", "helloServlet");

        // 3. 톰캣 시작
        tomcat.start();
    }
}
```

- **톰캣 설정**: 내장 톰캣 생성 후 커넥터로 8080 포트 연결
- **서블릿 등록**: `tomcat.addServlet()`으로 서블릿 등록, `addServletMappingDecoded()`로 URL 매핑
- **톰캣 시작**: `tomcat.start()`로 서버 가동

### 내장 톰캣으로 스프링 연동

```java
public class EmbedTomcatSpringMain {
    public static void main(String[] args) throws LifecycleException {
        // 1. 톰캣 설정
        Tomcat tomcat = new Tomcat();
        Connector connector = new Connector();
        connector.setPort(8080);
        tomcat.setConnector(connector);

        // 2. 스프링 컨테이너 생성
        AnnotationConfigWebApplicationContext appContext = 
            new AnnotationConfigWebApplicationContext();
        appContext.register(HelloConfig.class);  // 컨트롤러 등록

        // 3. 디스패처 서블릿 생성 + 스프링 컨테이너 연결
        DispatcherServlet dispatcher = new DispatcherServlet(appContext);

        // 4. 디스패처 서블릿을 서블릿 컨테이너에 등록
        Context context = tomcat.addContext("", "/");
        tomcat.addServlet("", "dispatcher", dispatcher);
        context.addServletMappingDecoded("/", "dispatcher");

        tomcat.start();
    }
}
```

**실행 흐름 정리:**
```
톰캣 설정 → 스프링 컨테이너 생성 → 컨트롤러 빈 등록 
→ DispatcherServlet 생성 (스프링 컨테이너 연결) 
→ DispatcherServlet을 서블릿 컨테이너에 등록 
→ "/" 경로 요청 시 DispatcherServlet → 스프링 컨트롤러 호출
```

> 내장 톰캣을 개발자가 직접 다룰 일은 거의 없다. **작동 원리 정도만 이해**하면 충분하다.

## 3. 빌드와 배포 — JAR의 한계

### 일반 JAR의 문제점

자바의 `main()` 메서드를 실행하려면 jar 형식으로 빌드해야 한다:

```groovy
// 일반 Jar 생성
task buildJar(type: Jar) {
    manifest {
        attributes 'Main-Class': 'hello.embed.EmbedTomcatSpringMain'
    }
    with jar
}
```

그런데 이 jar를 실행하면 **오류가 발생**한다! 왜?

jar 파일을 풀어보면 **우리가 만든 소스코드만** 들어있고, 스프링 라이브러리와 내장 톰캣 라이브러리가 전혀 포함되어 있지 않다.

**핵심 문제:**
> **JAR 파일은 JAR 파일을 포함할 수 없다!** (JAR 스펙의 한계)

WAR는 `WEB-INF/lib/` 안에 라이브러리 jar 파일을 포함할 수 있었지만, JAR는 이것이 불가능하다.

## 4. Fat Jar (Uber Jar)

### Fat Jar란?

JAR 안에 JAR를 넣을 수 없지만, **클래스(class)는 얼마든지 넣을 수 있다!**

라이브러리 jar 파일들을 풀어서 나온 `.class` 파일들을 모두 추출하여 하나의 jar에 포함시키는 방식이다. 라이브러리의 모든 클래스가 포함되므로 파일 크기가 커져서 "Fat(뚱뚱한) Jar"라고 부른다.

```groovy
// Fat Jar 생성
task buildFatJar(type: Jar) {
    manifest {
        attributes 'Main-Class': 'hello.embed.EmbedTomcatSpringMain'
    }
    duplicatesStrategy = DuplicatesStrategy.WARN
    from { configurations.runtimeClasspath.collect { 
        it.isDirectory() ? it : zipTree(it) 
    }}
    with jar
}
```

### Fat Jar의 장점

- 하나의 jar 파일에 **필요한 모든 라이브러리를 내장** 가능
- 내장 톰캣 라이브러리를 jar 내부에 포함 가능
- **하나의 jar 파일로** 배포부터 웹 서버 설치 + 실행까지 모든 것을 단순화

### Fat Jar의 단점

1. **어떤 라이브러리가 포함되어 있는지 확인이 어렵다**
   - 모든 것이 class로 풀려있어 어떤 라이브러리에서 온 것인지 추적 불가
   
2. **파일명 중복을 해결할 수 없다** ⚠️ (심각한 문제)
   - 서로 다른 라이브러리가 같은 경로/이름의 파일을 가지고 있으면 **하나만 포함**되고 나머지는 누락됨
   - 예: A 라이브러리와 B 라이브러리 모두 `META-INF/services/jakarta.servlet.ServletContainerInitializer` 파일을 가지고 있다면 하나만 선택됨
   - 정상 동작하지 않는 심각한 버그 유발

## 5. 스프링 부트 실행 가능 Jar (Executable Jar)

### Fat Jar의 문제를 해결한 스프링 부트만의 방식

스프링 부트는 **jar 내부에 jar를 포함할 수 있는 특별한 구조**의 jar를 만들었다.

| Fat Jar 문제 | 실행 가능 Jar 해결 |
|------------|----------------|
| 어떤 라이브러리인지 확인 어려움 | jar 내부에 jar가 그대로 있어 **어떤 라이브러리인지 바로 확인** |
| 파일명 중복 해결 불가 | 각 jar가 독립적이므로 **같은 경로의 파일도 모두 인식** |

### 실행 과정

`java -jar xxx.jar` 실행 시:

```
1. java -jar xxx.jar 실행
      ↓
2. META-INF/MANIFEST.MF 파일을 읽음
      ↓
3. Main-Class: org.springframework.boot.loader.JarLauncher 실행
   (우리가 만든 클래스가 아닌 스프링 부트가 넣어준 JarLauncher!)
      ↓
4. JarLauncher가 jar 내부의 jar를 읽어들이는 작업 수행
   - BOOT-INF/classes/ → 우리가 만든 클래스
   - BOOT-INF/lib/     → 외부 라이브러리 jar 파일들
      ↓
5. Start-Class: hello.boot.BootApplication의 main() 실행
   (우리가 실제로 만든 메인 클래스)
```

**MANIFEST.MF 내용:**
```
Manifest-Version: 1.0
Main-Class: org.springframework.boot.loader.JarLauncher
Start-Class: hello.boot.BootApplication
```

- `Main-Class`: 스프링 부트가 빌드 시 자동으로 넣어주는 **JarLauncher** — jar 내부의 jar를 읽어들이는 역할
- `Start-Class`: 우리가 실제로 만든 애플리케이션의 메인 클래스

> 실행 가능 Jar는 자바 표준이 아니라 **스프링 부트가 만든 독자적인 구조**이다. WAR의 구조를 본따서 만들어졌다.

## 6. 스프링 부트와 웹 서버

스프링 부트는 위의 모든 복잡한 과정을 **자동으로 처리**해준다.

### build.gradle

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
}
```

- `spring-boot-starter-web`의 의존관계를 따라가보면 내장 톰캣(`tomcat-embed-core`)이 포함되어 있다
- 스프링 부트는 **현재 부트 버전에 가장 적절한 외부 라이브러리 버전을 자동으로 선택**해주므로 버전을 명시하지 않아도 된다

### 스프링 부트 실행 과정

```java
@SpringBootApplication
public class BootApplication {
    public static void main(String[] args) {
        SpringApplication.run(BootApplication.class, args);
    }
}
```

`SpringApplication.run()` 내부에서 일어나는 2가지 핵심:

**1. 스프링 컨테이너 생성:**
```java
class ServletWebServerApplicationContextFactory implements ApplicationContextFactory {
    private ConfigurableApplicationContext createContext() {
        return new AnnotationConfigServletWebServerApplicationContext();
    }
}
```

**2. WAS(내장 톰캣) 생성:**
```java
@Override
public WebServer getWebServer(ServletContextInitializer... initializers) {
    Tomcat tomcat = new Tomcat();
    Connector connector = new Connector(this.protocol);
    // ...
    return getTomcatWebServer(tomcat);
}
```

> 스프링 부트의 `main()` 메서드 안에서 **스프링 컨테이너 생성 + WAS(내장 톰캣) 생성**이 모두 자동으로 이루어진다.
