# 섹션 6: 외부설정과 프로필 1

## 1. 외부 설정이란?

### 문제 상황

하나의 애플리케이션을 여러 환경에서 실행해야 한다:
- **개발 환경**: 개발 서버, 개발 DB 사용
- **운영 환경**: 운영 서버, 운영 DB 사용

### 기존 방식의 문제

환경에 따라 다른 코드로 빌드해서 각각의 jar 파일을 만드는 방식:

```
개발용 빌드 → dev-app.jar (개발 DB 설정 포함)
운영용 빌드 → prod-app.jar (운영 DB 설정 포함)
```

**문제점:**
1. 환경에 따라 **빌드를 여러 번** 해야 한다
2. 개발 버전과 운영 버전의 **빌드 결과물이 다르다** → 개발 환경에서의 검증이 운영 환경에서 보장되지 않음
3. 각 환경에 맞춰 나온 결과물이 **다른 환경에서 사용 불가**

### 올바른 해결: 외부 설정

> **유지보수하기 좋은 애플리케이션의 기본 원칙 = 변하는 것과 변하지 않는 것을 분리하는 것**

```
하나의 빌드 결과물(app.jar) + 환경별 외부 설정값
```

- 설정값을 **실행 시점에** 외부에서 주입
- 빌드를 **한 번만** 하면 되고, 개발 환경에서 검증한 결과물을 그대로 운영에서 사용 가능

## 2. 외부 설정 4가지 방법

| 방법 | 범위 | 설명 |
|------|------|------|
| **OS 환경 변수** | OS 전체 | 해당 OS를 사용하는 모든 프로세스에서 접근 |
| **자바 시스템 속성** | JVM | 해당 JVM 안에서만 접근 |
| **커맨드 라인 옵션 인수** | 애플리케이션 | `main(args)` 메서드로 전달 |
| **외부 파일(설정 데이터)** | 애플리케이션 | 프로그램에서 특정 파일을 직접 읽음 |

### 2-1. OS 환경 변수

OS를 사용하는 **모든 프로그램에서 읽을 수 있는** 전역 설정값:

```java
public static void main(String[] args) {
    Map<String, String> envMap = System.getenv();
    for (String key : envMap.keySet()) {
        log.info("env {}={}", key, System.getenv(key));
    }
}
```

- **장점**: 간단하게 설정 가능
- **단점**: 전역 변수 느낌 — 다른 프로그램에서도 접근 가능하므로 특정 애플리케이션에만 사용하고 싶다면 부적합

### 2-2. 자바 시스템 속성

실행한 **JVM 안에서만** 접근 가능한 외부 설정:

```bash
# 실행 시 -D 옵션으로 전달
java -Durl=devdb -Dusername=dev_user -Dpassword=dev_pw -jar app.jar
```

```java
public static void main(String[] args) {
    String url = System.getProperty("url");
    String username = System.getProperty("username");
    String password = System.getProperty("password");
    
    // 자바 코드로 설정도 가능
    System.setProperty("hello_key", "hello_value");
}
```

### 2-3. 커맨드 라인 인수

실행 시점에 `main(args)` 메서드의 `args` 파라미터로 전달:

```bash
java -jar app.jar url=devdb username=dev_user password=dev_pw
```

**문제점:** 파싱되지 않은 통 문자열이라 개발자가 `=` 기준으로 직접 파싱해야 한다.

### 커맨드 라인 옵션 인수 (스프링의 개선)

스프링은 `--`를 붙이면 `key=value` 형식으로 자동 파싱해준다:

```bash
java -jar app.jar --url=devdb --username=dev_user --password=dev_pw
```

```java
public static void main(String[] args) {
    ApplicationArguments appArgs = new DefaultApplicationArguments(args);
    
    // 옵션 이름 목록
    Set<String> optionNames = appArgs.getOptionNames();
    
    // 값 조회 (List<String> 반환 — 하나의 옵션에 2개 이상의 값 가능)
    List<String> url = appArgs.getOptionValues("url");
    List<String> username = appArgs.getOptionValues("username");
}
```

**스프링 빈에서 사용:**
```java
@Component
@RequiredArgsConstructor
public class CommandLineBean {
    private final ApplicationArguments arguments;  // 자동 주입

    @PostConstruct
    public void init() {
        log.info("source {}", List.of(arguments.getSourceArgs()));
        log.info("optionNames {}", arguments.getOptionNames());
    }
}
```

## 3. 외부 설정 — 스프링 통합 (Environment)

### 문제: 외부 설정마다 읽는 방법이 다르다

- OS 환경변수: `System.getenv(key)`
- 자바 시스템 속성: `System.getProperty(key)`
- 커맨드 라인 옵션 인수: `ApplicationArguments`

외부 설정 소스가 바뀌면 코드를 **모두 변경**해야 하는 문제가 있다.

### 해결: PropertySource + Environment 추상화

스프링은 **외부 설정의 위치에 상관없이** 일관된 방식으로 `key=value` 형식의 설정값을 읽을 수 있도록 추상화를 제공한다.

```
[OS 환경변수] → SystemEnvironmentPropertySource ─┐
[자바 시스템 속성] → SystemPropertySource ─────────┤
[커맨드 라인 인수] → CommandLinePropertySource ────┤→ Environment → 개발자
[설정 파일] → ApplicationConfigPropertySource ─────┘
```

**PropertySource**: 외부 설정을 조회하는 추상 클래스. 각 소스별 구현체가 있음
**Environment**: 모든 `PropertySource`를 통합하여 조회 기능 제공

```java
@Component
@RequiredArgsConstructor
public class EnvironmentCheck {
    private final Environment env;

    @PostConstruct
    public void init() {
        String url = env.getProperty("url");
        String username = env.getProperty("username");
        String password = env.getProperty("password");
    }
}
```

> `application.properties`, `application.yml`도 `PropertySource`에 추가되어 `Environment`를 통해 조회할 수 있다.

## 4. 우선순위

### 기본 원칙

1. **더 유연한 것**이 우선권을 가짐
   - 변경하기 어려운 파일 < 실행 시 원하는 값을 줄 수 있는 자바 시스템 속성
2. **범위가 좁은 것**이 우선권을 가짐
   - JVM 전체에서 접근 가능한 자바 시스템 속성 < main의 args로만 접근하는 커맨드 라인 옵션 인수

### 우선순위 (아래로 갈수록 높음)

```
1. 설정 데이터 (application.properties)     ← 가장 낮음
2. OS 환경변수
3. 자바 시스템 속성
4. 커맨드 라인 옵션 인수
5. @TestPropertySource (테스트에서 사용)     ← 가장 높음
```

## 5. 설정 데이터 — 외부 파일

### 방법 1: 외부 파일

각 서버에 `application.properties` 파일을 배치:
- 개발 서버: `url=dev.db.com`
- 운영 서버: `url=prod.db.com`

**단점:**
- 서버 10대면 10대 모두 파일을 각각 관리해야 함
- 설정 파일의 변경 이력 추적이 어려움

### 방법 2: 내부 파일 분리

프로젝트 내부에 환경별 설정 파일을 포함:

```
src/main/resources/
├── application-dev.properties    (개발용)
└── application-prod.properties   (운영용)
```

실행 시 **프로필**로 어떤 파일을 읽을지 결정:

```bash
# 개발 환경
java -jar app.jar --spring.profiles.active=dev

# 운영 환경  
java -jar app.jar --spring.profiles.active=prod
```

### 방법 3: 내부 파일 합체 (권장)

하나의 `application.properties` 안에서 `#---`로 논리적 영역을 구분:

```properties
# default 설정 (프로필 미지정 시 사용)
url=local.db.com
username=local_user
password=local_pw

#---
spring.config.activate.on-profile=dev
url=dev.db.com
username=dev_user
password=dev_pw

#---
spring.config.activate.on-profile=prod
url=prod.db.com
username=prod_user
password=prod_pw
```

**스프링 데이터 적용 순서:**
1. 위에 있는 **default 데이터**를 먼저 읽어 설정
2. 현재 활성 프로필에 해당하는 논리 문서를 찾아 **값을 대체**
3. 논리 문서에 없는 값은 default 값이 유지됨

### 설정 데이터 우선순위 (아래로 갈수록 높음)

```
1. jar 내부 application.properties
2. jar 내부 application-{profile}.properties
3. jar 외부 application.properties
4. jar 외부 application-{profile}.properties
```

> 프로필을 지정하지 않으면 **default** 프로필이 활성화된다.
