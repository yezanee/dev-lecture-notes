# 섹션 9: 마이크로미터, 프로메테우스, 그라파나

## 1. 마이크로미터 소개

### 모니터링의 필요성

서비스를 운영할 때 다음과 같은 지표들을 지속적으로 확인해야 한다:
- CPU, 메모리 사용량
- 커넥션 풀 사용량
- 고객 요청수

### 모니터링 툴 변경 문제

각 모니터링 툴(JMX, 프로메테우스, Datadog 등)마다 **데이터를 전달하는 포맷이 다르다**. 모니터링 툴을 변경하면 **관련 코드를 모두 변경**해야 하는 문제가 있다.

### 마이크로미터 (Micrometer) — 메트릭 추상화

마이크로미터는 **애플리케이션 메트릭 파사드(Facade)**라고 불린다:

```
[애플리케이션] → [마이크로미터 표준 API] → [구현체 선택]
                                            ├── 프로메테우스
                                            ├── Datadog
                                            ├── CloudWatch
                                            └── JMX ...
```

- 애플리케이션의 메트릭을 **마이크로미터가 정한 표준 방법**으로 모아서 제공
- 모니터링 툴을 변경해도 **구현체만 교체**하면 되고, 애플리케이션 코드는 변경 불필요
- **로그의 SLF4J와 유사한 역할** (SLF4J가 로그 추상화라면, 마이크로미터는 메트릭 추상화)

> 스프링 부트 액츄에이터는 마이크로미터를 기본으로 내장하고 있다.

### 마이크로미터가 지원하는 모니터링 툴

AppOptics, Atlas, CloudWatch, Datadog, Dynatrace, Elastic, Ganglia, Graphite, Humio, Influx, Instana, JMX, KairosDB, New Relic, **Prometheus**, SignalFx, Stackdriver, StatsD, Wavefront

## 2. 메트릭 확인하기

### metrics 엔드포인트

`GET http://localhost:8080/actuator/metrics`
→ 액츄에이터가 마이크로미터를 통해 등록한 기본 메트릭 목록 확인

`GET http://localhost:8080/actuator/metrics/{name}`
→ 특정 메트릭 상세 조회

### Tag 필터

Tag를 기반으로 메트릭을 필터링:

```
http://localhost:8080/actuator/metrics/jvm.memory.used?tag=area:heap
http://localhost:8080/actuator/metrics/jvm.memory.used?tag=area:nonheap
http://localhost:8080/actuator/metrics/http.server.requests?tag=uri:/log&tag=status:200
```

## 3. 기본 제공 메트릭

### JVM 메트릭 (`jvm.*`)
- 메모리 및 버퍼 풀 세부정보
- 가비지 수집(GC) 관련 통계
- 스레드 활용
- 로드/언로드된 클래스 수
- JVM 버전 정보, JIT 컴파일 시간

### 시스템 메트릭 (`system.*`, `process.*`, `disk.*`)
- CPU 지표
- 파일 디스크립터 메트릭
- 가동 시간(Uptime)
- 사용 가능한 디스크 공간

### 애플리케이션 시작 메트릭
- `application.started.time`: 애플리케이션 시작까지 걸린 시간 (`ApplicationStartedEvent`)
- `application.ready.time`: 요청 처리 준비까지 걸린 시간 (`ApplicationReadyEvent`)

### 스프링 MVC 메트릭 (`http.server.requests`)

스프링 MVC 컨트롤러가 처리하는 모든 요청을 자동 측정:

| Tag | 설명 |
|-----|------|
| `uri` | 요청 URI |
| `method` | GET, POST 등 |
| `status` | 200, 400, 500 등 |
| `exception` | 예외 정보 |
| `outcome` | 2xx→SUCCESS, 4xx→CLIENT_ERROR, 5xx→SERVER_ERROR |

### 데이터소스 메트릭 (`jdbc.connections.*`)
- 최대/최소/활성/대기 커넥션 수
- 히카리 커넥션 풀: `hikaricp.*`로 더 상세한 메트릭 확인 가능

### 로그 메트릭 (`logback.events`)
- trace, debug, info, warn, error 각 레벨별 로그 수
- **error 로그가 급격히 증가하면 위험 신호!**

### 톰캣 메트릭 (`tomcat.*`)

```yaml
server:
  tomcat:
    mbeanregistry:
      enabled: true  # 이 옵션을 켜야 톰캣 메트릭이 노출됨
```

최대 쓰레드, 사용 쓰레드 수 등 다양한 톰캣 메트릭 확인 가능

## 4. 프로메테우스와 그라파나

### 전체 아키텍처

```
[스프링 부트 앱]                    [프로메테우스]           [그라파나]
 └── 액츄에이터 + 마이크로미터         └── 메트릭 수집 DB      └── 대시보드
     └── 프로메테우스 구현체가           └── 주기적으로           └── 프로메테우스에서
         메트릭을 프로메테우스              앱의 메트릭을            데이터를 조회하여
         포맷으로 변환                    수집 & 저장              그래프로 표시
```

1. **스프링 부트 액츄에이터 + 마이크로미터** → 수많은 메트릭을 자동 생성
2. **마이크로미터 프로메테우스 구현체** → 프로메테우스가 읽을 수 있는 포맷으로 변환
3. **프로메테우스** → 메트릭을 **주기적으로 수집(Pull)**하여 내부 DB에 저장
4. **그라파나** → 프로메테우스에서 데이터를 조회하여 **그래프 대시보드** 제공

### 프로메테우스의 역할

- 메트릭을 **지속해서 수집**하고 DB에 **저장**
- 과거 이력 확인 가능

### 그라파나의 역할

- DB에 있는 데이터를 **시각화** (그래프, 차트)
- 수많은 **대시보드 템플릿** 제공
- 프로메테우스를 포함한 다양한 데이터소스 지원

## 5. 프로메테우스 — 기본 기능

### 용어 정리

- **태그(Tag)**: 마이크로미터에서의 용어
- **레이블(Label)**: 프로메테우스에서의 용어 (같은 개념)

### 필터 문법

레이블을 기준으로 `{}`를 사용하여 필터링:

```promql
# uri=/log 이고 method=GET인 요청만
http_server_requests_seconds_count{uri="/log", method="GET"}

# /actuator/prometheus 제외
http_server_requests_seconds_count{uri!="/actuator/prometheus"}

# method가 GET 또는 POST (정규식)
http_server_requests_seconds_count{method=~"GET|POST"}

# /actuator로 시작하는 uri 제외
http_server_requests_seconds_count{uri!~"/actuator.*"}
```

| 연산자 | 의미 |
|-------|------|
| `=` | 정확히 일치 |
| `!=` | 같지 않음 |
| `=~` | 정규식 일치 |
| `!~` | 정규식 불일치 |

### 연산자와 함수

```promql
# 합계
sum(http_server_requests_seconds_count)

# 그룹별 합계 (SQL의 GROUP BY와 유사)
sum by(method, status)(http_server_requests_seconds_count)

# 메트릭 수 카운트
count(http_server_requests_seconds_count)

# 상위 3개 메트릭
topk(3, http_server_requests_seconds_count)

# 10분 전 데이터 조회
http_server_requests_seconds_count offset 10m

# 지난 1분간의 모든 기록값 (범위 벡터 선택기)
http_server_requests_seconds_count[1m]
```

## 6. 게이지와 카운터

메트릭은 크게 **2가지**로 분류된다:

### 게이지 (Gauge)

- 임의로 **오르내릴 수 있는** 값
- 예: CPU 사용량, 메모리 사용량, 사용 중인 커넥션 수
- 현재 상태를 그대로 그래프에 출력하면 유의미한 정보가 됨

### 카운터 (Counter)

- 단순하게 **증가만 하는** 단일 누적값
- 예: HTTP 요청 수, 로그 발생 수
- 계속 증가하는 그래프만 보이므로 그대로 표시하면 유의미한 정보를 얻기 어려움

### 카운터의 상대적 증가 확인

**increase()** — 시간 단위별 증가량:
```promql
increase(http_server_requests_seconds_count{uri="/log"}[1m])
```
→ 분당 얼마나 요청이 증가했는지 확인

**rate()** — 초당 평균 증가율:
```promql
rate(http_server_requests_seconds_count{uri="/log"}[1m])
```
→ `[1m]`이면 60초 기준으로 나눈 값

**irate()** — 초당 순간 증가율:
→ 급격한 증가를 확인하기 좋음

> 프로메테우스의 단점은 한눈에 들어오는 대시보드를 만들기 어렵다는 점이다. 이 부분은 **그라파나**가 해결해준다.
