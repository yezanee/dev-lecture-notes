# 섹션 2: 커넥션 풀과 데이터소스 이해

## 1. 커넥션 풀 이해

### 데이터베이스 커넥션을 매번 새로 만들면?

커넥션을 새로 생성하는 과정은 매우 복잡하고 느리다:

```
1. 애플리케이션 → DB 드라이버에 커넥션 요청
2. DB 드라이버 → DB와 TCP/IP 연결 (3-way handshake)
3. DB 드라이버 → ID, PW, 부가 정보를 DB에 전달
4. DB → 인증 완료 후 내부에 DB 세션 생성
5. DB → 커넥션 생성 완료 응답
6. DB 드라이버 → 커넥션 객체를 클라이언트에 반환
```

**문제점:**
- TCP/IP 연결을 포함한 네트워크 동작이 필요 → **시간이 많이 소모**됨
- 매 요청마다 이 과정을 반복 → **사용자 응답 속도에 직접적 영향**
- SQL 실행 시간 + 커넥션 생성 시간 → 전체 지연 증가

### 커넥션 풀이란?

**미리 커넥션을 만들어놓고 풀(Pool)에 보관**하는 방식:

```
[커넥션 풀 - 애플리케이션 시작 시]
┌─────────────────────────────────┐
│  conn0  conn1  conn2  ... conn9 │  ← 기본 10개의 커넥션을 미리 생성
│  (TCP/IP 연결 완료 상태)          │  ← 이미 DB와 연결되어 있음
└─────────────────────────────────┘
```

### 커넥션 풀 사용 흐름

```
[요청 시]
1. 애플리케이션 → 커넥션 풀에서 커넥션 하나를 "빌려옴" (새로 생성하지 않음!)
   - 이미 TCP/IP로 DB에 연결된 상태 → 즉시 SQL 전달 가능

[사용 후]
2. 커넥션을 close()하면 → 연결을 끊는 것이 아니라 풀에 "반납"
   - 커넥션은 살아있는 상태로 풀에 돌아감
   - 다음 요청이 재사용
```

### 정리

| 항목 | 설명 |
|------|------|
| 풀 크기 | 서비스 특성, 서버 스펙, DB 성능에 따라 결정 (기본 10개) |
| 장점 | DB에 무한정 연결 생성 방지, 응답 속도 향상 |
| 대표 구현체 | commons-dbcp2, tomcat-jdbc pool, **HikariCP** |
| **현재 표준** | **HikariCP** (스프링 부트 2.0부터 기본) |

> 실무에서는 커넥션 풀을 항상 기본으로 사용한다.

## 2. DataSource 이해

### 문제: 커넥션 획득 방법이 바뀌면?

커넥션을 획득하는 방법은 여러 가지가 있다:
- `DriverManager`를 직접 사용 (매번 새로 생성)
- `HikariCP` 커넥션 풀 사용
- `DBCP2` 커넥션 풀 사용

```java
// DriverManager 방식
Connection con = DriverManager.getConnection(url, username, password);

// HikariCP 방식
HikariDataSource ds = new HikariDataSource();
Connection con = ds.getConnection();
```

**문제**: `DriverManager`에서 `HikariCP`로 변경하면 **애플리케이션 코드도 함께 변경**해야 한다!

### 해결: DataSource 인터페이스 (추상화)

자바는 `javax.sql.DataSource`라는 **커넥션 획득 방법을 추상화**하는 인터페이스를 제공한다:

```java
public interface DataSource {
    Connection getConnection() throws SQLException;
}
```

```
[애플리케이션 코드] → [DataSource 인터페이스] → [구현체]
                     getConnection()           ├── HikariDataSource
                                               ├── DBCP2DataSource
                                               └── DriverManagerDataSource (스프링 제공)
```

- 대부분의 커넥션 풀이 `DataSource` 인터페이스를 구현
- 개발자는 `DataSource` 인터페이스**에만 의존**하면 됨
- 구현체를 변경해도 **애플리케이션 코드는 변경 불필요** (DI/OCP)

### 설정과 사용의 분리 — 핵심 설계 원칙

**DriverManager 방식** (설정과 사용이 섞여있음):
```java
// 매번 커넥션을 가져올 때마다 URL, USERNAME, PASSWORD를 전달해야 함
Connection con1 = DriverManager.getConnection(URL, USERNAME, PASSWORD);
Connection con2 = DriverManager.getConnection(URL, USERNAME, PASSWORD);
```

**DataSource 방식** (설정과 사용이 분리됨):
```java
// [설정] — 한 번만 수행
DriverManagerDataSource dataSource = new DriverManagerDataSource(URL, USERNAME, PASSWORD);

// [사용] — 필요할 때마다 호출 (설정 정보를 몰라도 됨!)
Connection con1 = dataSource.getConnection();
Connection con2 = dataSource.getConnection();
```

> **"설정과 관련된 속성들은 한 곳에 있는 것이 향후 변경에 더 유연하게 대처할 수 있다."**
>
> 사용하는 쪽(Repository)은 `DataSource`만 알면 되고, URL/USERNAME/PASSWORD 같은 설정 정보를 몰라도 된다.

## 3. DataSource 예제 — DriverManager vs HikariCP

### DriverManagerDataSource 사용

```java
@Test
void dataSourceDriverManager() throws SQLException {
    // [설정]
    DriverManagerDataSource dataSource = 
        new DriverManagerDataSource(URL, USERNAME, PASSWORD);
    
    // [사용]
    Connection con1 = dataSource.getConnection();
    Connection con2 = dataSource.getConnection();
    log.info("connection={}, class={}", con1, con1.getClass());
    log.info("connection={}, class={}", con2, con2.getClass());
}
```

**결과**: `conn0`, `conn1` — **매번 새로운 커넥션** 생성

### HikariDataSource (커넥션 풀) 사용

```java
@Test
void dataSourceConnectionPool() throws SQLException, InterruptedException {
    // [설정]
    HikariDataSource dataSource = new HikariDataSource();
    dataSource.setJdbcUrl(URL);
    dataSource.setUsername(USERNAME);
    dataSource.setPassword(PASSWORD);
    dataSource.setMaximumPoolSize(10);
    dataSource.setPoolName("MyPool");
    
    // [사용]
    Connection con1 = dataSource.getConnection();
    Connection con2 = dataSource.getConnection();
    log.info("connection={}, class={}", con1, con1.getClass());
    log.info("connection={}, class={}", con2, con2.getClass());

    Thread.sleep(1000);  // 커넥션 풀에서 커넥션 생성 로그 확인용
}
```

**실행 로그 분석:**

```
# 1. HikariCP 설정 확인
HikariConfig - MyPool - configuration:
HikariConfig - maximumPoolSize: 10

# 2. 별도 스레드에서 커넥션 10개를 비동기로 생성 (앱 시작 지연 방지!)
MyPool connection adder - Added connection conn0
MyPool connection adder - Added connection conn1
...

# 3. 커넥션 풀 상태
MyPool - pool stats: total=10, active=2, idle=8, waiting=0
         ↑ 전체 10개    ↑ 사용중 2개  ↑ 대기중 8개
```

**핵심 관찰:**
- 커넥션 풀에서 커넥션 10개를 채우는 작업은 **별도 스레드**에서 비동기로 수행 → 애플리케이션 시작 시간에 영향 없음
- `con1`, `con2` 모두 **conn0을 재사용** → 풀에서 빌려쓰고 반납하는 방식

## 4. DataSource 적용 — MemberRepositoryV1

### 변경 전 (V0): DriverManager 직접 사용

```java
// 매번 DriverManager에서 커넥션을 직접 가져옴
private Connection getConnection() {
    return DBConnectionUtil.getConnection();  // DriverManager 사용
}
```

### 변경 후 (V1): DataSource 주입

```java
@Slf4j
public class MemberRepositoryV1 {
    
    private final DataSource dataSource;  // DataSource를 외부에서 주입받음
    
    public MemberRepositoryV1(DataSource dataSource) {
        this.dataSource = dataSource;
    }
    
    private Connection getConnection() throws SQLException {
        Connection con = dataSource.getConnection();  // DataSource로 커넥션 획득
        log.info("get connection={}, class={}", con, con.getClass());
        return con;
    }
    
    private void close(Connection con, Statement stmt, ResultSet rs) {
        JdbcUtils.closeResultSet(rs);      // 스프링이 제공하는 편의 유틸
        JdbcUtils.closeStatement(stmt);
        JdbcUtils.closeConnection(con);    // 커넥션 풀이면 풀에 반환!
    }
    
    // save, findById, update, delete는 V0와 동일한 구조
    // (getConnection() 방식만 변경됨)
}
```

**변경된 점:**
1. `DataSource`를 **생성자 주입**으로 받음 → 외부에서 구현체 결정
2. `DBConnectionUtil` 제거 → `dataSource.getConnection()` 사용
3. `JdbcUtils` 사용 → 리소스 정리를 편리하게 (커넥션 풀이면 `close()` 시 풀에 반환)

### DI의 위력

```java
// DriverManager 사용 시
MemberRepositoryV1 repository = new MemberRepositoryV1(
    new DriverManagerDataSource(URL, USERNAME, PASSWORD)
);

// HikariCP로 변경해도 Repository 코드는 전혀 변경 없음!
MemberRepositoryV1 repository = new MemberRepositoryV1(
    new HikariDataSource()  // 설정 후 주입
);
```

> `MemberRepositoryV1`은 `DataSource` 인터페이스에만 의존하므로, `DriverManagerDataSource` → `HikariDataSource`로 변경해도 **Repository 코드는 한 줄도 변경하지 않는다.** 이것이 DI와 OCP(개방-폐쇄 원칙)의 힘이다.
