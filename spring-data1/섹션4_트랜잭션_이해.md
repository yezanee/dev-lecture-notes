# 섹션 4: 트랜잭션 이해

## 1. 트랜잭션이란?

**트랜잭션(Transaction)** = 거래. 데이터베이스에서 하나의 거래를 안전하게 처리하도록 보장해주는 것.

### 대표적인 예: 계좌이체

A가 B에게 2000원을 이체한다면:
1. A의 잔고를 2000원 감소
2. B의 잔고를 2000원 증가

이 두 작업은 **반드시 함께 성공하거나 함께 실패**해야 한다. 만약 1번만 성공하고 2번이 실패하면? A의 돈만 사라지는 심각한 문제 발생!

### 커밋(Commit)과 롤백(Rollback)

- **커밋**: 모든 작업이 성공 → 데이터베이스에 **정상 반영**
- **롤백**: 작업 중 하나라도 실패 → 거래 이전 상태로 **되돌림**

## 2. ACID 속성

트랜잭션은 다음 4가지를 보장해야 한다:

| 속성 | 설명 | 예시 |
|------|------|------|
| **원자성(Atomicity)** | 트랜잭션 내 작업은 모두 성공하거나 모두 실패 | 이체의 출금+입금이 하나의 단위 |
| **일관성(Consistency)** | 트랜잭션 전후로 DB의 무결성 제약 조건 유지 | 잔고는 0 이상이어야 함 |
| **격리성(Isolation)** | 동시 실행 트랜잭션이 서로 영향을 주지 않음 | 동시 이체 시 정합성 유지 |
| **지속성(Durability)** | 성공한 트랜잭션의 결과는 영구적으로 저장 | 커밋 후 서버 다운되어도 데이터 유지 |

> 격리성을 완벽히 보장하려면 동시 처리 성능이 매우 나빠진다. 그래서 **트랜잭션 격리 수준(Isolation Level)**으로 조절한다:
> - READ UNCOMMITTED (가장 낮음)
> - READ COMMITTED (일반적으로 사용)
> - REPEATABLE READ
> - SERIALIZABLE (가장 높음, 가장 느림)

## 3. 데이터베이스 연결 구조와 DB 세션

```
[클라이언트 1] ──커넥션──→ [DB 서버]
                            ├── 세션 1 (트랜잭션 관리)
[클라이언트 2] ──커넥션──→   ├── 세션 2
[커넥션 풀]   ──커넥션──→   └── 세션 3, 4, 5...
```

- 클라이언트가 DB에 접속하면 DB 서버 내부에 **세션**이 생성됨
- 세션이 SQL을 실행하고, 트랜잭션을 시작/커밋/롤백함
- 커넥션 풀의 각 커넥션마다 별도의 세션이 연결됨

> 커밋하기 전까지 변경 데이터는 **해당 세션에서만 보인다**. 다른 세션에서는 커밋 전 데이터를 볼 수 없다 (READ COMMITTED 기준).

## 4. 자동 커밋과 수동 커밋

### 자동 커밋 (기본값)

```sql
set autocommit true;  -- 자동 커밋 모드 (기본)
insert into member(member_id, money) values ('data1', 10000);  -- 즉시 커밋됨!
insert into member(member_id, money) values ('data2', 10000);  -- 즉시 커밋됨!
```

- 각 SQL이 실행되는 **즉시 자동으로 커밋**
- 편리하지만 **트랜잭션 기능을 제대로 사용할 수 없음**
- 두 번째 SQL이 실패해도 첫 번째는 이미 커밋되어 롤백 불가

### 수동 커밋 (트랜잭션 시작)

```sql
set autocommit false;  -- 수동 커밋 모드 = 트랜잭션 시작!
insert into member(member_id, money) values ('data1', 10000);
insert into member(member_id, money) values ('data2', 10000);
commit;  -- 두 작업 모두 반영
-- 또는
rollback;  -- 두 작업 모두 취소
```

> **`set autocommit false`를 설정하는 것이 곧 트랜잭션을 시작한다는 의미**다. 이후 `commit` 또는 `rollback`을 호출해야 트랜잭션이 종료된다.

## 5. DB 락 (Lock)

### 락이 필요한 이유

세션 1이 memberA의 금액을 500으로 변경하는 동안(아직 커밋 전), 세션 2도 memberA의 금액을 변경하려 한다면? → **데이터 정합성 문제 발생**

### 락 동작 방식

```
[세션 1] update member set money=500 where member_id='memberA'
         → memberA의 락 획득 ✅ → 변경 수행

[세션 2] update member set money=1000 where member_id='memberA'
         → memberA의 락 획득 시도 → 대기... ⏳
         → 세션 1이 커밋/롤백하면 락이 반납됨
         → 세션 2가 락을 획득하고 변경 수행 ✅
```

- 데이터를 변경(INSERT, UPDATE, DELETE)하려면 해당 행(row)의 **락을 먼저 획득**해야 함
- 락을 획득하지 못하면 **대기** (타임아웃 시간을 설정할 수 있음)
- 트랜잭션이 커밋/롤백되면 락이 반납됨

### 조회와 락: SELECT FOR UPDATE

일반적인 SELECT는 락을 획득하지 않는다. 하지만 **조회한 데이터를 기반으로 변경할 예정**이라면 조회 시점에 락을 걸어야 한다:

```sql
select * from member where member_id='memberA' for update;
```

→ 조회와 동시에 **락을 획득**하여, 다른 세션이 해당 데이터를 변경하지 못하게 방지

## 6. 트랜잭션 적용 — 애플리케이션 구현

### 핵심 원칙: 트랜잭션은 비즈니스 로직이 있는 서비스 계층에서 시작해야 한다

```
[Controller] → [Service] → [Repository]
                 ↑ 트랜잭션 시작/종료는 여기서!
```

왜? 비즈니스 로직이 잘못되면 함께 롤백해야 하므로, 비즈니스 로직의 시작과 끝에 맞춰 트랜잭션을 관리해야 한다.

### 핵심 문제: 같은 커넥션 유지

트랜잭션을 사용하려면 **시작부터 끝까지 같은 커넥션(같은 세션)**을 사용해야 한다.

```java
// MemberRepositoryV2 — 커넥션을 파라미터로 전달받음
public Member findById(Connection con, String memberId) throws SQLException {
    // con을 외부에서 받아서 사용 (새로 생성하지 않음!)
    // ...
}

public void update(Connection con, String memberId, int money) throws SQLException {
    // con을 외부에서 받아서 사용
    // ...
}
```

```java
// MemberServiceV2 — 트랜잭션 관리
public void accountTransfer(String fromId, String toId, int money) throws SQLException {
    Connection con = dataSource.getConnection();
    try {
        con.setAutoCommit(false);  // 트랜잭션 시작!

        // 비즈니스 로직 (같은 커넥션 전달)
        Member fromMember = memberRepository.findById(con, fromId);
        Member toMember = memberRepository.findById(con, toId);

        memberRepository.update(con, fromId, fromMember.getMoney() - money);
        memberRepository.update(con, toId, toMember.getMoney() + money);

        con.commit();  // 성공 시 커밋

    } catch (Exception e) {
        con.rollback();  // 실패 시 롤백
        throw new IllegalStateException(e);
    } finally {
        release(con);  // autoCommit을 true로 복원 후 커넥션 반납
    }
}
```

### release에서 autoCommit을 복원하는 이유

커넥션 풀을 사용하면 `con.close()`가 커넥션을 종료하는 것이 아니라 **풀에 반납**한다. 이때 `autoCommit = false` 상태가 유지되면 다음 사용자가 의도치 않게 수동 커밋 모드를 사용하게 된다.

```java
private void release(Connection con) {
    if (con != null) {
        try {
            con.setAutoCommit(true);  // 풀에 반납하기 전에 기본값으로 복원!
            con.close();  // 커넥션 풀에 반납
        } catch (Exception e) {
            log.info("error", e);
        }
    }
}
```

### 이 방식의 문제점 (다음 섹션에서 해결)

1. **서비스 계층에 JDBC 기술이 누수** — `Connection`, `SQLException` 등 JDBC 의존성이 서비스에 침투
2. **커넥션을 파라미터로 넘기는 번거로움** — 모든 Repository 메서드에 `Connection` 파라미터 추가 필요
3. **트랜잭션 관련 반복 코드** — `try-catch-finally`, `setAutoCommit`, `commit`, `rollback`이 매번 반복
