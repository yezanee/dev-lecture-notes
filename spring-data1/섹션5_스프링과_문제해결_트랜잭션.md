# 섹션 5: 스프링과 문제 해결 — 트랜잭션

## 1. 기존 방식의 문제점

섹션 4에서 구현한 `MemberServiceV2`에는 심각한 문제들이 있다:

### 문제 1: 트랜잭션 코드의 반복

```java
// 모든 서비스 메서드마다 이 패턴이 반복됨
Connection con = dataSource.getConnection();
try {
    con.setAutoCommit(false);  // 트랜잭션 시작
    bizLogic(...);             // 비즈니스 로직
    con.commit();
} catch (Exception e) {
    con.rollback();
    throw new IllegalStateException(e);
} finally {
    release(con);
}
```

### 문제 2: JDBC 기술 누수

서비스 계층은 **순수한 비즈니스 로직**만 있어야 하는데, `Connection`, `SQLException`, `DataSource` 같은 **JDBC 기술에 의존**하고 있다.

→ 나중에 JDBC를 JPA로 변경하면 **서비스 코드를 전부 수정**해야 함!

### 문제 3: 커넥션 파라미터 전달

트랜잭션을 유지하려고 Repository 메서드마다 `Connection` 파라미터를 넘겨야 한다.

### 문제 4: 예외 누수

`SQLException`은 JDBC 기술에 종속적인 체크 예외. 서비스에서 `throws SQLException`을 선언해야 하므로 JDBC에 의존하게 됨.

## 2. 트랜잭션 추상화

### 문제: 구현 기술마다 트랜잭션 코드가 다르다

```java
// JDBC 트랜잭션
con.setAutoCommit(false);
// ... 비즈니스 로직 ...
con.commit();

// JPA 트랜잭션
transaction.begin();
// ... 비즈니스 로직 ...
transaction.commit();
```

JDBC → JPA로 변경하면 트랜잭션 코드도 변경해야 한다.

### 해결: PlatformTransactionManager

스프링은 **트랜잭션 추상화 인터페이스**를 제공한다:

```java
public interface PlatformTransactionManager extends TransactionManager {
    TransactionStatus getTransaction(TransactionDefinition definition) 
        throws TransactionException;
    void commit(TransactionStatus status) throws TransactionException;
    void rollback(TransactionStatus status) throws TransactionException;
}
```

```
[서비스 계층] → [PlatformTransactionManager] → [구현체]
                getTransaction()                ├── DataSourceTransactionManager (JDBC)
                commit()                        ├── JpaTransactionManager (JPA)
                rollback()                      └── HibernateTransactionManager
```

- 서비스는 `PlatformTransactionManager` **인터페이스에만 의존**
- JDBC → JPA로 변경해도 서비스 코드는 **변경 불필요** (구현체만 교체)

## 3. 트랜잭션 동기화

### 문제: 커넥션을 어떻게 같은 것으로 유지하는가?

기존에는 Repository 메서드에 `Connection` 파라미터를 넘겨서 해결했다. 이는 지저분하고 유지보수가 어렵다.

### 해결: 트랜잭션 동기화 매니저 (TransactionSynchronizationManager)

스프링은 **ThreadLocal**을 사용해 커넥션을 동기화한다:

```
1. 트랜잭션 매니저 → 커넥션 생성 → 트랜잭션 시작
2. 트랜잭션 매니저 → 커넥션을 "트랜잭션 동기화 매니저"에 보관 (ThreadLocal)
3. Repository → 트랜잭션 동기화 매니저에서 커넥션을 꺼내 사용
4. 트랜잭션 종료 → 동기화 매니저에서 커넥션을 꺼내 commit/rollback → 커넥션 반납
```

- **ThreadLocal**을 사용하므로 멀티스레드 환경에서도 안전하게 각자의 커넥션 유지
- Repository에서 커넥션을 가져올 때 `DataSourceUtils.getConnection(dataSource)` 사용

### MemberRepositoryV3 — 파라미터 없이 커넥션 유지

```java
// 이전: 커넥션을 파라미터로 전달
public Member findById(Connection con, String memberId) { ... }

// 개선: DataSourceUtils로 동기화된 커넥션 획득
public Member findById(String memberId) throws SQLException {
    String sql = "select * from member where member_id = ?";
    Connection con = null;
    PreparedStatement pstmt = null;
    ResultSet rs = null;

    try {
        // 트랜잭션 동기화 매니저에서 커넥션을 가져옴!
        con = DataSourceUtils.getConnection(dataSource);
        pstmt = con.prepareStatement(sql);
        pstmt.setString(1, memberId);
        rs = pstmt.executeQuery();
        // ...
    } finally {
        // close가 아닌 release — 트랜잭션 중이면 커넥션을 유지
        DataSourceUtils.releaseConnection(con, dataSource);
    }
}
```

**`DataSourceUtils.getConnection()`의 동작:**
- 트랜잭션 동기화 매니저에 커넥션이 있으면 → 그 커넥션 반환 (같은 커넥션 유지!)
- 없으면 → 새 커넥션 생성

**`DataSourceUtils.releaseConnection()`의 동작:**
- 트랜잭션이 진행 중이면 → 커넥션을 닫지 않고 유지
- 트랜잭션이 없으면 → 커넥션을 닫음

## 4. MemberServiceV3_1 — 트랜잭션 매니저 사용

```java
@RequiredArgsConstructor
public class MemberServiceV3_1 {
    private final PlatformTransactionManager transactionManager;
    private final MemberRepositoryV3 memberRepository;

    public void accountTransfer(String fromId, String toId, int money) {
        // 트랜잭션 시작
        TransactionStatus status = transactionManager.getTransaction(
            new DefaultTransactionDefinition()
        );

        try {
            // 비즈니스 로직
            bizLogic(fromId, toId, money);
            transactionManager.commit(status);  // 성공 시 커밋

        } catch (Exception e) {
            transactionManager.rollback(status);  // 실패 시 롤백
            throw new IllegalStateException(e);
        }
        // finally에서 release 불필요! 트랜잭션 매니저가 알아서 처리
    }
}
```

**개선된 점:**
- `Connection`을 직접 다루지 않음 → JDBC 의존 감소
- 파라미터로 커넥션을 전달하지 않음
- `release()` 직접 호출 불필요

## 5. MemberServiceV3_2 — 트랜잭션 템플릿

### 아직 남은 문제: 트랜잭션 코드 반복

```java
// 모든 서비스 메서드에 이 패턴이 반복
TransactionStatus status = transactionManager.getTransaction(...);
try {
    bizLogic(...);
    transactionManager.commit(status);
} catch (Exception e) {
    transactionManager.rollback(status);
    throw new IllegalStateException(e);
}
```

### 해결: TransactionTemplate

스프링의 **템플릿 콜백 패턴**을 적용하여 반복 코드 제거:

```java
public class MemberServiceV3_2 {
    private final TransactionTemplate txTemplate;
    private final MemberRepositoryV3 memberRepository;

    public MemberServiceV3_2(PlatformTransactionManager transactionManager,
                              MemberRepositoryV3 memberRepository) {
        this.txTemplate = new TransactionTemplate(transactionManager);
        this.memberRepository = memberRepository;
    }

    public void accountTransfer(String fromId, String toId, int money) {
        txTemplate.executeWithoutResult((status) -> {
            try {
                // 비즈니스 로직만!
                bizLogic(fromId, toId, money);
            } catch (SQLException e) {
                throw new IllegalStateException(e);
            }
        });
        // commit, rollback은 TransactionTemplate이 자동으로 처리!
    }
}
```

**개선된 점:**
- `commit()`, `rollback()` 코드가 사라짐
- 트랜잭션 시작/종료 로직을 `TransactionTemplate`이 대신 처리
- 비즈니스 로직에 **더 집중** 가능

**남은 문제:**
- 서비스에 여전히 트랜잭션 처리 기술(`TransactionTemplate`)이 존재
- 비즈니스 로직과 트랜잭션 기술이 한 곳에 섞여있음

## 6. MemberServiceV3_3 — @Transactional (AOP)

### 프록시를 통한 관심사 분리

```
[기존] 클라이언트 → 서비스 (트랜잭션 코드 + 비즈니스 로직)

[AOP] 클라이언트 → 트랜잭션 프록시 → 서비스 (비즈니스 로직만!)
                   ↑ 트랜잭션 시작/커밋/롤백을 대신 처리
```

### @Transactional 적용

```java
public class MemberServiceV3_3 {
    private final MemberRepositoryV3 memberRepository;

    public MemberServiceV3_3(MemberRepositoryV3 memberRepository) {
        this.memberRepository = memberRepository;
    }

    @Transactional  // 이 한 줄이 트랜잭션 처리를 모두 대신함!
    public void accountTransfer(String fromId, String toId, int money) throws SQLException {
        bizLogic(fromId, toId, money);
    }

    private void bizLogic(String fromId, String toId, int money) throws SQLException {
        Member fromMember = memberRepository.findById(fromId);
        Member toMember = memberRepository.findById(toId);
        memberRepository.update(fromId, fromMember.getMoney() - money);
        memberRepository.update(toId, toMember.getMoney() + money);
    }
}
```

**핵심 변화:**
- 서비스에는 **순수한 비즈니스 로직만** 남음
- `@Transactional` 어노테이션 하나로 트랜잭션 처리 완료
- 스프링 AOP가 **프록시**를 만들어 트랜잭션을 시작/커밋/롤백

### @Transactional 동작 원리

```
1. 스프링 컨테이너 시작
2. @Transactional이 붙은 클래스의 프록시 객체 생성
3. 프록시 객체가 스프링 빈으로 등록됨

[호출 시]
4. 클라이언트 → 프록시 호출
5. 프록시가 트랜잭션 시작 (트랜잭션 매니저 사용)
6. 프록시가 실제 서비스의 비즈니스 로직 호출
7. 비즈니스 로직 완료 후 프록시가 커밋 또는 롤백
```

> 이것을 **선언적 트랜잭션 관리**라고 한다. 어노테이션 하나를 "선언"하는 것만으로 트랜잭션이 적용된다. (반대로 직접 코드를 작성하는 것은 "프로그래밍 방식 트랜잭션 관리")

## 7. 스프링 부트의 자동 리소스 등록

스프링 부트를 사용하면 다음 빈들이 **자동으로 등록**된다:

### DataSource 자동 등록

`application.properties`에 설정만 하면 자동으로 `HikariDataSource`가 빈으로 등록:

```properties
spring.datasource.url=jdbc:h2:tcp://localhost/~/test
spring.datasource.username=sa
spring.datasource.password=
```

### PlatformTransactionManager 자동 등록

- 현재 등록된 라이브러리를 보고 **적절한 트랜잭션 매니저를 자동 선택**
- JDBC 사용 → `DataSourceTransactionManager`
- JPA 사용 → `JpaTransactionManager`

> 덕분에 개발자는 `DataSource`와 `TransactionManager`를 직접 빈으로 등록할 필요가 없다.

## 정리: 진화 과정

```
V1: JDBC 직접 사용 → 모든 문제 존재
V2: 커넥션 파라미터 전달 → 트랜잭션 가능, but 서비스에 JDBC 코드 범벅
V3_1: PlatformTransactionManager → 트랜잭션 추상화 + 동기화
V3_2: TransactionTemplate → 반복 코드 제거
V3_3: @Transactional → 서비스에 순수 비즈니스 로직만 남음 ✅
```
