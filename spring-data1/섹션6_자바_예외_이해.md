# 섹션 6: 자바 예외 이해

## 1. 예외 계층 구조

자바의 예외는 다음과 같은 계층으로 구성된다:

```
Object
  └── Throwable            ← 최상위 예외
        ├── Error          ← 시스템 오류 (복구 불가능 — 잡으면 안 됨)
        │     ├── OutOfMemoryError
        │     └── StackOverflowError
        │
        └── Exception      ← 애플리케이션 예외
              ├── IOException         ← 체크 예외
              ├── SQLException        ← 체크 예외
              └── RuntimeException    ← 언체크 예외 (런타임 예외)
                    ├── NullPointerException
                    ├── IllegalArgumentException
                    └── IllegalStateException
```

**핵심 구분:**
- **`Error`**: 메모리 부족, 시스템 오류 등 **복구 불가능**한 예외. 개발자가 잡으면 안 됨
- **`Exception`** (RuntimeException 제외): **체크 예외** — 컴파일러가 체크
- **`RuntimeException`**: **언체크 예외** — 컴파일러가 체크하지 않음

## 2. 예외 기본 규칙

### 규칙 1: 예외는 잡아서 처리하거나 던져야 한다

```java
// 방법 1: 잡아서 처리
try {
    repository.call();
} catch (MyException e) {
    // 예외 처리 로직
}

// 방법 2: 밖으로 던지기
public void callThrow() throws MyException {
    repository.call();
}
```

### 규칙 2: 상위 예외를 catch하면 하위 예외도 함께 잡힌다

```java
catch (Exception e) {  // Exception의 모든 하위 예외를 잡음
    // IOException, SQLException, RuntimeException 등 모두 여기서 처리됨
}
```

> `Throwable`을 잡으면 `Error`까지 잡히므로 주의. 일반적으로 `Exception`부터 잡는다.

## 3. 체크 예외 (Checked Exception)

### 정의

`Exception`을 상속받은 예외 (단, `RuntimeException` 제외). **컴파일러가 예외 처리를 강제**한다.

```java
// 체크 예외 정의
public class MyCheckedException extends Exception {
    public MyCheckedException(String message) {
        super(message);
    }
}
```

### 사용 방법

```java
// 잡아서 처리
try {
    repository.call();
} catch (MyCheckedException e) {
    log.info("예외 처리, message={}", e.getMessage(), e);
}

// 또는 던지기 — throws 선언 필수!
public void callThrow() throws MyCheckedException {
    repository.call();
}
```

> **체크 예외는 `catch`하지 않으면 반드시 `throws`를 선언해야 한다.** 선언하지 않으면 **컴파일 오류** 발생!

### 장단점

| | 설명 |
|--|------|
| **장점** | 컴파일러가 예외 누락을 체크해주는 **안전장치** |
| **단점** | 처리할 수 없는 예외도 항상 `throws` 선언 필요 → **의존성 문제** |

## 4. 언체크 예외 (Unchecked Exception = 런타임 예외)

### 정의

`RuntimeException`을 상속받은 예외. 컴파일러가 예외 처리를 **강제하지 않는다**.

```java
// 언체크 예외 정의
public class MyUncheckedException extends RuntimeException {
    public MyUncheckedException(String message) {
        super(message);
    }
}
```

### 사용 방법

```java
// 잡아서 처리 (선택적)
try {
    repository.call();
} catch (MyUncheckedException e) {
    log.info("예외 처리, message={}", e.getMessage(), e);
}

// 던지기 — throws 선언 생략 가능!
public void callThrow() {  // throws 없어도 됨
    repository.call();
}
```

### 장단점

| | 설명 |
|--|------|
| **장점** | 신경 쓰고 싶지 않은 예외를 무시할 수 있어 **의존관계 문제 해결** |
| **단점** | 개발자가 실수로 예외를 누락할 가능성 |

## 5. 체크 예외 활용 — 실무에서의 문제

### 기본 원칙 2가지

1. **기본적으로 언체크(런타임) 예외를 사용**
2. 체크 예외는 **비즈니스 로직상 의도적으로 던져야 하는 예외**에만 사용
   - 예: 잔고 부족 예외, 결제 실패 예외 등 → 반드시 처리해야 하는 비즈니스 상황

### 체크 예외의 심각한 문제 1: 복구 불가능한 예외

대부분의 시스템 예외(`SQLException`, `ConnectException` 등)는 애플리케이션 레벨에서 **복구가 불가능**하다. DB가 다운되었는데 애플리케이션에서 무엇을 할 수 있겠는가?

그런데 체크 예외이기 때문에 **처리할 수 없어도** `catch`하거나 `throws`를 선언해야 한다.

### 체크 예외의 심각한 문제 2: 의존 관계 문제

```java
// JDBC를 사용하는 서비스
class MemberService {
    public void logic() throws SQLException, ConnectException {
        // ...
    }
}
```

만약 JDBC → JPA로 변경하면?
```java
// JPA로 변경 시 — 서비스의 throws 선언도 수정 필요!
class MemberService {
    public void logic() throws JPAException {  // 변경!
        // ...
    }
}
```

**서비스 계층이 특정 기술(JDBC)의 예외에 의존하게 되어**, 기술을 변경할 때 서비스 코드까지 수정해야 한다.

### "그러면 `throws Exception`으로 퉁치면 안 되나요?"

```java
public void logic() throws Exception {  // 모든 예외를 던짐
```

→ 다른 체크 예외를 체크할 수 있는 기능이 무효화됨. **안티 패턴**이므로 절대 사용하지 말 것.

## 6. 언체크 예외 활용 — 올바른 해결

### 런타임 예외로 전환

체크 예외를 **런타임 예외로 변환**하면 의존관계 문제를 해결할 수 있다:

```java
// 런타임 예외 정의
public class RuntimeSQLException extends RuntimeException {
    public RuntimeSQLException(Throwable cause) {
        super(cause);  // 원본 예외를 반드시 포함!
    }
}
```

```java
// Repository에서 변환
public void call() {
    try {
        runSQL();
    } catch (SQLException e) {
        throw new RuntimeSQLException(e);  // 체크 → 언체크 변환
    }
}
```

```java
// Service — throws 선언이 필요 없음! JDBC에 의존하지 않음!
class MemberService {
    public void logic() {  // throws 없음
        repository.call();
        networkClient.call();
    }
}
```

### 변환 후 구조

```
[Controller] → [Service] → [Repository]
                             catch(SQLException)
                             throw RuntimeSQLException(e)  ← 여기서 변환

Service는 RuntimeSQLException이 올라와도
throws 선언이 필요 없으므로 JDBC에 의존하지 않음!

최종적으로 공통 예외 처리(ControllerAdvice 등)에서 처리
```

### 현재 추세

최근 라이브러리들(JPA, Spring 등)은 대부분 **런타임 예외를 기본 제공**한다. 런타임 예외는 문서화가 중요하며, 필요시 코드에 `throws` 선언으로 예외를 명시할 수 있다.

## 7. 예외 포함과 스택 트레이스 ⚠️

예외를 전환할 때 **반드시 기존 예외를 포함**해야 한다!

### 올바른 방법 (기존 예외 포함)

```java
catch (SQLException e) {
    throw new RuntimeSQLException(e);  // e를 전달 → 원본 스택 트레이스 유지!
}
```

로그 출력:
```
RuntimeSQLException: ...
Caused by: java.sql.SQLException: DB 연결 실패  ← 원본 원인 확인 가능!
    at Repository.call(...)
```

### 잘못된 방법 (기존 예외 미포함)

```java
catch (SQLException e) {
    throw new RuntimeSQLException();  // e를 전달하지 않음 → 원본 정보 손실!
}
```

로그 출력:
```
RuntimeSQLException: ...
    at Service.logic(...)
// Caused by가 없음! 원본 원인을 알 수 없음!
```

> **기존 예외를 포함하지 않으면 실제 DB에서 발생한 예외의 원인을 확인할 수 없다.** 실무에서 이 실수를 하면 장애 원인 파악이 극도로 어려워진다. 반드시 `new RuntimeException(e)`처럼 원본 예외를 포함시켜야 한다!
