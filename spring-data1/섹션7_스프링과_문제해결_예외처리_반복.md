# 섹션 7: 스프링과 문제 해결 — 예외 처리, 반복

## 1. 체크 예외와 인터페이스

### 문제: 인터페이스에 특정 기술의 체크 예외가 침투

Repository를 인터페이스로 만들어 **구현 기술을 쉽게 교체**하고 싶다. 그런데 JDBC를 사용하면 `SQLException`(체크 예외)이 발생하므로:

```java
// 인터페이스에 JDBC 의존성이 들어감!
public interface MemberRepository {
    Member save(Member member) throws SQLException;  // JDBC에 종속!
    Member findById(String memberId) throws SQLException;
}
```

→ 이 인터페이스를 JPA로 구현하면 `throws JPAException`으로 바꿔야 한다
→ 인터페이스를 만든 **의미가 없어짐**

### 해결: 런타임 예외 사용

런타임 예외는 `throws` 선언이 필요 없으므로 인터페이스를 깔끔하게 유지할 수 있다:

```java
// 깔끔한 인터페이스
public interface MemberRepository {
    Member save(Member member);        // throws 없음!
    Member findById(String memberId);
}
```

## 2. 런타임 예외 적용 — MemberRepositoryV4_1

### 커스텀 런타임 예외 정의

```java
public class MyDbException extends RuntimeException {
    public MyDbException() {}
    public MyDbException(String message) { super(message); }
    public MyDbException(String message, Throwable cause) { super(message, cause); }
    public MyDbException(Throwable cause) { super(cause); }
}
```

### Repository에서 예외 변환

```java
public class MemberRepositoryV4_1 implements MemberRepository {

    @Override
    public Member save(Member member) {  // throws 없음!
        String sql = "insert into member(member_id, money) values(?, ?)";
        // ...
        try {
            // JDBC 코드
        } catch (SQLException e) {
            throw new MyDbException(e);  // 체크 → 런타임 변환! (원본 포함!)
        } finally {
            close(con, pstmt, null);
        }
    }
}
```

### Service 계층 — 순수해짐

```java
@Transactional
public void accountTransfer(String fromId, String toId, int money) {
    bizLogic(fromId, toId, money);
    // SQLException이 없어졌으므로 JDBC에 의존하지 않음!
}
```

## 3. 데이터 접근 예외 직접 만들기

### 문제: 특정 DB 예외를 복구하고 싶다면?

예를 들어 **키 중복 오류** 시 새로운 ID를 생성하여 재시도하는 로직이 필요하다면?

`MyDbException`만 있으면 **모든 DB 예외가 동일하게 취급**되어 특정 예외만 골라 처리할 수 없다.

### 해결: 특정 예외 클래스 생성

```java
public class MyDuplicateKeyException extends MyDbException {
    public MyDuplicateKeyException() {}
    public MyDuplicateKeyException(String message) { super(message); }
    public MyDuplicateKeyException(String message, Throwable cause) { super(message, cause); }
    public MyDuplicateKeyException(Throwable cause) { super(cause); }
}
```

### DB 에러 코드를 확인하여 적절한 예외로 변환

```java
catch (SQLException e) {
    // H2 DB의 키 중복 에러 코드: 23505
    if (e.getErrorCode() == 23505) {
        throw new MyDuplicateKeyException(e);  // 특정 예외로 변환
    }
    throw new MyDbException(e);  // 그 외 일반 DB 예외
}
```

```java
// Service에서 특정 예외만 복구
try {
    repository.save(new Member(memberId, 0));
} catch (MyDuplicateKeyException e) {
    log.info("키 중복, 복구 시도");
    String retryId = generateNewId(memberId);  // 새 ID 생성
    repository.save(new Member(retryId, 0));    // 재시도
}
```

### 남은 문제

- DB마다 에러 코드가 다름 (H2: 23505, MySQL: 1062 등)
- 수십~수백 개의 에러 코드를 모두 직접 매핑하는 것은 비현실적

## 4. 스프링 예외 추상화 ⭐

### 스프링이 제공하는 데이터 접근 예외 계층

스프링은 **데이터 접근 계층의 수십 가지 예외를 정리**하여 일관된 예외 계층을 제공한다:

```
DataAccessException (RuntimeException)  ← 최상위
  ├── NonTransientDataAccessException   ← 같은 SQL 재시도 시 실패
  │     ├── BadSqlGrammarException
  │     └── DuplicateKeyException       ← 키 중복!
  │
  └── TransientDataAccessException      ← 같은 SQL 재시도 시 성공 가능
        ├── QueryTimeoutException
        └── OptimisticLockingFailureException
```

**핵심 분류:**
- **Transient(일시적)**: 동일한 SQL을 다시 시도하면 **성공할 수 있음** (예: 타임아웃, 락 경합)
- **NonTransient(비일시적)**: 같은 SQL을 반복해도 **항상 실패** (예: 문법 오류, 키 중복)

### SQLExceptionTranslator — 자동 변환

```java
SQLExceptionTranslator exTranslator = 
    new SQLErrorCodeSQLExceptionTranslator(dataSource);

DataAccessException resultEx = exTranslator.translate(
    "select",     // 작업 설명
    sql,          // 실행한 SQL
    e             // 원본 SQLException
);
```

- 스프링이 내부에서 `sql-error-codes.xml`을 읽어 **각 DB별 에러 코드를 매핑**
- H2, MySQL, Oracle, PostgreSQL 등 **주요 DB를 모두 지원**
- `SQLException`의 에러 코드를 보고 적절한 스프링 예외(`DuplicateKeyException` 등)로 **자동 변환**

### 적용 — MemberRepositoryV4_2

```java
public class MemberRepositoryV4_2 implements MemberRepository {
    
    private final DataSource dataSource;
    private final SQLExceptionTranslator exTranslator;

    public MemberRepositoryV4_2(DataSource dataSource) {
        this.dataSource = dataSource;
        this.exTranslator = new SQLErrorCodeSQLExceptionTranslator(dataSource);
    }

    @Override
    public Member save(Member member) {
        String sql = "insert into member(member_id, money) values(?, ?)";
        // ...
        try {
            // JDBC 코드
        } catch (SQLException e) {
            // 스프링 예외로 자동 변환!
            throw exTranslator.translate("save", sql, e);
        }
    }
}
```

**장점:**
- 직접 에러 코드를 매핑할 필요 없음
- DB 종류가 바뀌어도 **같은 스프링 예외 계층 사용**
- JDBC → JPA로 변경해도 서비스에서 `DuplicateKeyException`을 잡는 코드는 **변경 불필요**

## 5. JDBC 반복 문제 해결 — JdbcTemplate

### 아직 남은 문제: JDBC 코드의 극심한 반복

모든 Repository 메서드에서 반복되는 패턴:

```java
// 이 패턴이 모든 메서드에 반복됨
Connection con = null;
PreparedStatement pstmt = null;
ResultSet rs = null;
try {
    con = getConnection();
    pstmt = con.prepareStatement(sql);
    // 파라미터 바인딩
    // SQL 실행
    // 결과 매핑
} catch (SQLException e) {
    throw exTranslator.translate(...);
} finally {
    close(con, pstmt, rs);
}
```

### 해결: JdbcTemplate

스프링의 `JdbcTemplate`은 위의 반복 코드를 **모두 자동으로 처리**해준다:

```java
public class MemberRepositoryV5 implements MemberRepository {
    
    private final JdbcTemplate template;

    public MemberRepositoryV5(DataSource dataSource) {
        this.template = new JdbcTemplate(dataSource);
    }

    @Override
    public Member save(Member member) {
        String sql = "insert into member(member_id, money) values(?, ?)";
        template.update(sql, member.getMemberId(), member.getMoney());
        return member;
    }

    @Override
    public Member findById(String memberId) {
        String sql = "select * from member where member_id = ?";
        return template.queryForObject(sql, memberRowMapper(), memberId);
    }

    @Override
    public void update(String memberId, int money) {
        String sql = "update member set money=? where member_id=?";
        template.update(sql, money, memberId);
    }

    @Override
    public void delete(String memberId) {
        String sql = "delete from member where member_id=?";
        template.update(sql, memberId);
    }

    private RowMapper<Member> memberRowMapper() {
        return (rs, rowNum) -> {
            Member member = new Member();
            member.setMemberId(rs.getString("member_id"));
            member.setMoney(rs.getInt("money"));
            return member;
        };
    }
}
```

### JdbcTemplate이 자동으로 처리하는 것

| 항목 | 설명 |
|------|------|
| 커넥션 획득/반납 | DataSource를 통해 자동 관리 |
| PreparedStatement 생성/닫기 | 자동 |
| ResultSet 처리/닫기 | 자동 |
| **예외 변환** | `SQLException` → 스프링 예외 자동 변환 |
| **트랜잭션 동기화** | 트랜잭션 매니저와 자동 연동 |
| 반복 코드 제거 | try-catch-finally 불필요 |

## 전체 정리: 문제 → 해결 과정

```
[V0] JDBC 직접 사용
 ├── 문제: 반복 코드, JDBC 의존, 예외 처리
 ↓
[V1] DataSource 적용 → 커넥션 풀 추상화
 ↓
[V2] 커넥션 파라미터 전달 → 트랜잭션 가능 (but 서비스에 JDBC 코드)
 ↓
[V3_1] PlatformTransactionManager → 트랜잭션 추상화
[V3_2] TransactionTemplate → 트랜잭션 반복 코드 제거
[V3_3] @Transactional → AOP로 서비스 계층 순수화
 ↓
[V4_1] 런타임 예외 변환 → 서비스의 체크 예외 의존 제거
[V4_2] 스프링 예외 추상화 → DB별 에러 코드 자동 매핑
 ↓
[V5] JdbcTemplate → JDBC 반복 코드 완전 제거 ✅
```

> 최종적으로 서비스 계층은 `@Transactional` 하나만으로 트랜잭션을 처리하고, Repository는 `JdbcTemplate`으로 간결하게 데이터에 접근하며, 예외는 스프링이 자동으로 추상화해준다.
